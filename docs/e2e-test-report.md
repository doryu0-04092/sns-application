- **一回きりの手動実行であり、CI では再実行できない。** 回帰検出の手段としては残らない。
  だから証跡（スクリーンショット・ネットワークログ・トレース）を厚く残している。
  （2026-08-26 追記: この限界を受けて、9章の1〜3を Playwright で自動化した。
  本レポートの位置づけは変わらない。以下は実施時点の記録である）

  開発スタック（実データ24投稿）に対するもので、前回7章はシード済み（2万投稿・画像0枚）である。

- **動画は撮っていない。** 使用した chrome-devtools MCP に録画機能が無いため、

### なぜ 5173 の本番ビルドで実施したか

**S3バケットのCORSが単一オリジン固定だから。**
[docker/localstack/init-s3.sh](../docker/localstack/init-s3.sh) は
`AllowedOrigins: ["http://localhost:5173"]` を設定しており、
バックエンド側も `application.yml` の `app.cors.allowed-origin` が既定 `http://localhost:5173`
（`CorsConfig.java` は `List.of(allowedOrigin)` で1件しか許可しない）。

ブラウザは署名付きURLで LocalStack へ**直接 PUT** するため、
4173（preview の既定ポート）で動かすとプリフライトで落ちる。
それは今回検証したい未確認パスそのものなので、
`--port 5173` を指定して**本番ビルドを 5173 で配信**した。
これで「本番と同じ成果物」と「CORSが通るオリジン」を両立できる。

| **アクセストークン失効時のサイレント更新** | **合格** | `GET /auth/me` 401 → `POST /auth/refresh` 200 → `GET /auth/me` 200 → 画面継続。**ユーザーには何も起きていないように見える** |

#### トークン失効の作り方と、その限界

クッキーを消すのではなく、**バックエンドを別のJWT秘密鍵で再起動**して失効させた。
リフレッシュトークンはJWTではなくDBにハッシュ保存されているため、
「アクセストークンだけが無効・リフレッシュトークンは有効」という状態を正確に再現できる。
ファイルは一切変更せず、シェルの環境変数で上書きし、検証後に元の構成へ戻している。

**ただしこれは署名検証の失敗であって、有効期限(exp)切れではない。**
15分経過による自然失効の経路は通していない。
`JwtAuthFilter` はどちらも同じ401に落とすが、経路が違う点は明記しておく。

## 3. 見つかった不具合

### 3-1. BUG-1【高】日時が全画面で UTC オフセット分ずれて表示される（修正済み）

**症状。** 作成した直後の投稿・コメントが「**9時間**」と表示される（JST = UTC+9）。

**実測。**

| 項目 | 値 |
|---|---|
| DB の `created_at` | `2026-08-26 07:42:28`（UTC、`timestamp without time zone`） |
| DB の `now()` | `2026-08-26 07:45:46+00`（= 3分前の投稿） |
| APIのレスポンス | `"createdAt":"2026-08-26T07:42:28.430169"` — **タイムゾーン指定子なし** |
| 画面表示 | **「9時間」** |

**原因。** ECMAScript の仕様上、`new Date("2026-08-26T07:42:28.430169")` のように
**オフセットを持たない日時形式はローカル時刻として解釈される**。
値の中身はUTCなのに、ブラウザはJSTとして読むため、実際より9時間古い時刻になる。

```
frontend/src/utils/time.ts:2
  const date = new Date(iso);   // iso にオフセットが無い → ローカル時刻として解釈
```

**影響範囲。** タイムライン・投稿詳細・コメント・プロフィールの**すべての日時**。
7日を超えると `YYYY/MM/DD` 表記に切り替わるが、こちらも同じ理由で
**日付境界付近では1日ずれる**。

**なぜ既存テストで捕まらなかったか。** ここが重要な点で、
`frontend/src/utils/time.test.ts:26` のコメントは
「`new Date()` はこれをローカル時刻として解釈する」と正しく述べたうえで、
**テスト側も同じ前提でローカル時刻の文字列を組み立てている**。
実APIのペイロード（オフセット無しのUTC値）を一度も通していないため、
**テストとバグが同じ思い込みを共有していて、何件書いても検出できない構造**になっていた。

**証跡。** `docs/e2e/01-timeline-mobile-images.png`、`docs/e2e/04-post-detail-mobile.png`

#### 修正の内容

**バックエンドで、欠けていたタイムゾーン情報を補う**方針を採った。
不具合の所在が表示ではなく**APIの契約**にあるためである。
フロントは「オフセットが無い日時はローカル時刻」という言語仕様どおりに動いていただけで、
表示側で辻褄を合わせると、次に日時を使う実装が同じ罠を踏み直す。

`PostResponse` / `CommentResponse` の `createdAt` / `updatedAt`（計4フィールド）に
`@JsonFormat` を付け、`2026-08-26T07:42:28.430169Z` の形式で返すようにした。
パターンは `JsonFormats.UTC_DATE_TIME` に集約し、2つのDTOで表記がずれないようにしている。

**値がUTCだと言い切れる根拠**は同定数のコメントに残した。
日時はすべてDBの `now()` 由来で、DBセッションのタイムゾーンはUTC、
列は `TIMESTAMP`（タイムゾーン無し）である。
よって `LocalDateTime` として読んだ値はUTCの壁時計時刻そのもので、
`Z` を付けることは**値の意味を変えずに欠けていた情報を補う操作**にあたる。

列を `TIMESTAMPTZ` にすればこの前提を型で保証できるが、
既存データの解釈変更を伴うため本修正には含めていない。

**フロントのプロダクトコードは1行も変えていない。** 契約が正しくなれば
`new Date(iso)` がそのまま正しく動くためである。
変更したのはテスト側で、`time.test.ts` の `secondsAgo` が
ローカル時刻の文字列を組み立てていた箇所を `toISOString()` に戻し、
`test/fixtures.ts` の日時リテラル4件を実形式に合わせた。

#### 修正後の検証

`docs/openapi.json` を再生成し（差分8行）、生成TS型も更新した。
**バックエンド487件・フロント168件がすべて成功**し、`npm run build`（型検査）と `oxlint` も通っている。

そのうえで**実ブラウザで再確認した**。今回の不具合は「テストが緑なのに壊れていた」類なので、
テストの成功だけを根拠にしないためである。
ブラウザのタイムゾーンオフセットが **-540分（JST、不具合が出る条件そのもの）** の環境で、

| 対象 | 修正前 | 修正後 |
|---|---|---|
| 投稿した直後の投稿 | 「9時間」 | **「たった今」** |
| 約35分前・40分前の投稿 | （9時間ずれた値） | **「35分」「40分」** |
| 8月8日深夜(UTC)の投稿 | 「2026/08/08」 | **「2026/08/09」** |

3行目が、レポート本文で「日付境界付近では1日ずれる」と書いた点の**実地での裏付け**になった。
UTCで8月8日の深夜にあたる投稿はJSTでは8月9日であり、修正前は1日古い日付を表示していた。

**証跡。** `docs/e2e/05-bug1-fixed-relative-time.png`

### 3-2. BUG-2【中】画像の読み込みに失敗するとアイコン表示が崩れる（修正済み）

**症状。** 丸いアイコン枠から `alt` テキストがはみ出し、破損アイコンと重なって表示される。

**原因。** `frontend/src/components/Avatar.tsx` は
`avatarUrl` が非nullなら必ず `<img>` を描画し、**`onError` のフォールバックを持たない**。
頭文字を表示する分岐は `avatarUrl` が無い場合にしか働かない。

**誘発条件。** S3上のオブジェクトが存在しない場合、または**署名付きURLの期限切れ**
（`X-Amz-Expires=86400` = 24時間。ページを開いたまま日をまたぐと該当しうる）。

**証跡。** `docs/e2e/04-post-detail-mobile.png`（佐藤 陽菜のアイコン）

#### 修正の内容と検証

`onError` で**読み込みに失敗したURLを記録し、頭文字表示へ切り替える**ようにした。

真偽値ではなくURLを覚えているのは、プロフィール編集で新しいアイコンに差し替わったときに
「前のURLで失敗した」状態を引きずって頭文字のままになるのを避けるためである。
この分岐は単体テストで固定した（`Avatar.test.tsx`。別URLに変わったら再び画像を出すこと）。

検証は**実際に壊れた状態を再現して**行った。
LocalStack はS3オブジェクトを永続化しないため、スタックを再起動すると
DBの `avatar_key` が存在しないオブジェクトを指す状態が自然に発生する。

| | 修正前 | 修正後 |
|---|---|---|
| 破損したまま描画される `<img>` | **6枚以上**（alt テキストが丸枠からはみ出す） | **0枚** |
| 表示 | 破損アイコンと文字の重なり | **頭文字の丸アイコン** |

**証跡。** `docs/e2e/06-bug2-fixed-avatar-fallback.png`

### 3-3. BUG-3【低】404 を3回リトライしている（修正済み）

存在しない投稿を開くと `GET /api/posts/999999` が **4回**（初回+3リトライ）発行され、
その間「読み込み中...」が表示され続ける。
「この投稿は見つかりませんでした。」が出るまで**約2.5秒**かかった。

`QueryClient` は `staleTime` を設定しているが `retry` は既定（3回）のままである。
**404は再試行しても結果が変わらない**。

#### 修正の内容と検証

判定を `api/retry.ts` の `shouldRetryQuery` に切り出し、
**4xx は回数に関係なく即座に打ち切る**ようにした。
再試行に意味があるのは通信の瞬断や 5xx のような一時的な失敗だけである。

401 も再試行しない。アクセストークン失効からの復帰は
`apiFetch` がリフレッシュ＋1回だけの再実行で既に吸収しており（`client.ts`）、
そこを通ってなお401なら送り直しても通らないためである。

関数として切り出したのは、`QueryClient` の設定のままだと単体テストで固定できないから。
`retry.test.ts` で 4xx／5xx／`ApiError` でない失敗／回数上限を網羅した。

| | 修正前 | 修正後 |
|---|---|---|
| `GET /api/posts/999999` のリクエスト数 | **4回**（初回+3リトライ） | **1回** |
| 「見つかりませんでした」表示までの時間 | 約 **2.5秒** | **即時**（計測分解能100ms未満） |

### 3-4. OBS-2【低】フォーム入力に `id`/`name`/`autocomplete` が無い（修正済み）

ブラウザのコンソールが `A form field element should have an id or name attribute` と
`Input elements should have autocomplete attributes (suggested: "current-password")` を報告していた。
機能上の不具合ではないが、**パスワードマネージャの自動補完が効かない**。

#### 修正の内容と検証

アプリ内の全フォーム要素に `id` / `name` を付け、認証まわりには `autocomplete` を指定した
（ログインは `username` / `current-password`、サインアップは `nickname` / `username` / `new-password`）。

**コメント欄と編集欄には `id` を付けていない。** これらはコメントの数だけ描画されるため、
固定の `id` を付けると DOM 内で重複して不正なHTMLになる。
ブラウザの指摘は「`id` **または** `name`」なので `name` だけで満たせる。

あわせて `ProfileEditPage` の `<label>` に `htmlFor` を追加した。
ラベルが入力欄の兄弟要素として置かれていて紐付いておらず、
**ラベルをクリックしても入力欄にフォーカスが移らない**状態だったため。

検証: ログイン画面の**コンソール出力が2件から0件になった**ことを実ブラウザで確認した。

「シードデータに画像を1枚も含めなかった(`imgCount: 0`)。`loading="lazy"` 欠如・サイズ指定なし・
サムネイル未生成・転送量の**いずれも未検証**」「**全画面 CLS 0.00 という結果は
『問題なし』の証拠にならない**」としていた。実際に画像を投稿して測った。

### 4-1. 事実として確認できたこと

| 懸念 | 実測 | 判定 |
|---|---|---|
| `loading="lazy"` が無い | 全 `<img>` が `loading="auto"` | **懸念どおり** |
| `width`/`height` の指定が無い | 全 `<img>` で属性が `null` | **懸念どおり** |
| サムネイル生成が無い | 1600×1200 (573,738 B) と 1200×900 (369,110 B) を **241×192 CSS px** で表示。アイコンも 800×800 (72,028 B) を **44×44** で表示 | **懸念どおり** |
| サイズ指定が無いとCLSが悪化する | **CLS 0.00** | **懸念は成立しなかった** |

### 4-2. CLS が悪化しなかった理由

**CSS 側が先に領域を確保しているため。** 投稿画像は固定の高さを持つグリッドに入り、
アイコンも `h-11 w-11` のように寸法が決まっている。
画像が届く前から箱の大きさが決まっているので、`width`/`height` 属性が無くてもずれない。

**したがって「サイズ指定が無い＝CLS悪化」という事前の推測は、この画面構成では誤りだった。**
前回 CLS 0.00 だったのは「ずれる対象が無かったから」であると同時に、
**画像を入れても 0.00 のままである**ことが今回確認できた。

### 4-3. 転送量は実害として残る（OBS-1）

モバイル（412×915、DPR 2.625、CPU 4x、Fast 4G）で `/home` を計測した結果。

| 指標 | 値 |
|---|---|
| LCP | **2,109 ms** |
| LCP内訳 | TTFB 3 ms / **Load delay 1,140 ms** / **Load duration 911 ms** / Render delay 55 ms |
| CLS | **0.00** |
| Chrome「画像配信の改善」の削減見込み | **926.5 kB** |
| Chrome「キャッシュ」の削減見込み | 943.7 kB（S3応答に `cache-control` が無い） |

**注目すべきはLCPの内訳が前回と逆転している点。**
前回（画像0枚）は LCP 1,384 ms のうち 1,381 ms が render delay で、
「サーバが遅いのではなくJSの解析・実行が支配的」という結論だった。
今回は **LCP要素が画像になり、その読み込み（Load delay + Load duration = 2,051 ms）が支配的**である。

Chrome の指摘は具体的で、投稿画像1枚あたり
「表示サイズ(256×192)に対してファイルが大きすぎる(994×1200)」として
レスポンシブ化で 550.1 kB、WebP/AVIF化で 375 kB の削減余地を挙げている。

**ただしこれは前回値との比較には使えない。** データ量も画像の有無も条件が違う。
言えるのは「**画像を1投稿に2枚付けると約921KBを転送し、それがLCPの主因になる**」という
この条件下での事実だけである。

### 4-4. 対応: アップロード前にブラウザ側で縮小する（OBS-1）

原寸のまま保存していることが転送量の直接の原因なので、
**保存する前に縮小する**方針を採った（`utils/image.ts`）。

長辺が **1600px** を超える画像だけを縮小する。投稿詳細は幅600px程度で表示されるため、
2倍の画素密度の画面でも足りる。それ以下の画像は再エンコードしない
（開くたびに劣化を重ねても得るものが無い）。

**形式は変えない。** PNG を JPEG にすれば軽くなるが透過が失われ、
透過アイコンを上げた利用者の画像が黒く潰れる。軽さのために見た目を壊さない。
**アニメーションGIFは canvas を通さない**（1コマ目だけになるため）。
縮小に失敗した場合は元のファイルをそのまま使う。最適化のために投稿できなくなる方が損失が大きい。

実ブラウザで 4000×3000 の写真を投稿して確認した。

| | アップロード前 | 保存後 |
|---|---|---|
| 寸法 | 4000×3000 | **1600×1200** |
| サイズ | 1,201,210 B | **246,509 B（79.5%削減）** |

#### この対応で解決しないこと

**一覧の過剰取得は残る。** タイムラインは 241×192 で表示するので、
1600px の画像はそこでも大きすぎる。これを詰めるには表示サイズ別の画像を用意する必要があり、
サムネイル生成の仕組み（画像処理・キー設計・既存画像の移行）が要る。本対応の範囲を超えるため見送った。

**既にアップロード済みの画像には効かない。** 縮小はアップロード経路でのみ行う。

## 6. 仕様どおりであることを確認した挙動

一見すると不具合に見えるが、設計として意図されているもの。**現状を固定する意味で記録する。**

| 挙動 | 実測 |

| `unlike` / `unfollow` の冪等性 | 存在しない投稿への `DELETE .../like` は **200**、`POST` は **404**。フォローも同様。[test-plan.md](test-plan.md) 6.2 の非対称な契約どおり |

| 文字数境界 | 279文字→残り1・送信可、280文字→残り0・送信可、281文字→残り-1・**送信不可** |
| 絵文字の文字数 | サロゲートペアが2文字として数えられる（既知の現挙動） |
| 他人のプロフィール編集 | `/users/9/edit` を直接開くと `/users/9` へリダイレクト |
| 未定義URL | 404画面（ヘッダー無し・「タイムラインへ戻る」導線のみ） |

### 全角スペースのみの本文について（ドキュメントの補足）

[test-plan.md](test-plan.md) 6.2 は「全角スペースだけの本文は投稿できる」を
現状固定の挙動として記録しているが、**これはUIからは再現できない**。

サーバ側の `@NotBlank` は Java の `String.trim()` を使い U+3000 を除去しないため通ってしまうが、
フロントの送信可否は `body.trim().length > 0` で判定しており、
**JavaScript の `trim()` は Unicode 空白（U+3000 を含む）を除去する**。
そのため「投稿する」ボタンが無効のままになる。

つまり**この抜け穴はAPIを直接叩いた場合にのみ到達する**。
ドキュメントの記述は誤りではないが、UIからの到達可否まで書き添えるとより正確になる。

## 8. この検証の限界

| 限界 | 内容 |
|---|---|
| **一回きりで再実行できない** | 手動駆動のため CI に載らない。回帰検出には Playwright 等での資産化が必要（→9章）。**2026-08-26 に9章の1〜3を自動化した** |
| **同時実行の検証をしていない** | 単一ブラウザ・2ユーザーでの逐次操作。リフレッシュトークンの競合や、同時いいねの一意制約違反は再現していない |
| **失効は署名不一致で作った** | 有効期限(exp)切れの経路は通していない（→2章） |
| **性能値は比較に使えない** | データ量・画像の有無が前回と違う。絶対値の観測に留まる |
| **UIから誘発できない異常系は対象外** | 壊れたJSON・未定義HTTPメソッド・必須パラメータ欠落は L2 の担当 |
| **既存の開発DBを使っている** | 既存7ユーザー分のデータが混在。まっさらな状態からの検証ではない |
| **アイコン画像の一部が壊れた状態だった** | LocalStack はS3オブジェクトを永続化しない設定のため、過去に登録された `avatar_key` の参照先が失われていた（下記） |

### 環境上の注意（アプリの不具合ではない）

`docker-compose.yml` の LocalStack には**永続化ボリュームが無い**。
そのため `docker compose down` / `up` を挟むとアップロード済みのS3オブジェクトが消え、
DBに残った `avatar_key` が存在しないオブジェクトを指す。
本検証中に見えた「壊れたアイコン」の大半はこれが原因である。
**ただしその状況で表示が崩れること自体は BUG-2 というアプリ側の課題**であり、両者は分けて扱う。

## 9. Playwright での資産化（1〜3は実装済み）

今回の検証は再実行できない。資産化するなら、**壊れたときの損害が大きい順**に次の順序を推奨する。

1. **認証の往復** — サインアップ→ログアウト→ログイン→保護ルートのリダイレクト … **実装済み**
2. **投稿→コメント→返信→ツームストーン** — 状態遷移が最も複雑で、他機能への波及も大きい … **実装済み**
3. **画像アップロード** — presign→S3直PUT→promote の3者連携。ここは jsdom で代替できない … **実装済み**
4. **トークン失効時のサイレント更新** — 壊れると全ユーザーが突然ログアウトする … 未着手
5. **いいね／フォローの楽観的更新とロールバック** … 未着手

**2026-08-26 に 1〜3 を実装した**（`frontend/e2e/` に計10件）。実行方法は [README](../README.md) の「テスト」を参照。

着手前の懸念だった `data-testid` は、**全面付与ではなく3か所に限定した**。
`getByRole` / `getByLabel` で一意に指せる箇所は本番コードを変更せずに書けたためで、
目印が要ったのは DOM 上の絞り込みが避けられない箇所だけだった。
付与したのは `post-card`（タイムライン上の投稿の特定）、`post-image`（アバター画像との区別）、
`comment-node`（入れ子になった返信の特定）の3つである。
ツームストーンの文言は仕様そのものなので、目印を付けず可視テキストで検証している。
