# デプロイ中にしか確認できないこと

## これは何か

**環境が上がっている間にしか確認できない項目の一覧。**

AWS 上の環境は使うたびに作って壊す運用（[aws-architecture.md](aws-architecture.md)）なので、
上がっている時間が確認の機会のすべてになる。ここを取りこぼすと、
**次の機会まで未検証のまま残り、確認のためだけにもう一度課金することになる。**

2026-08-30 のデプロイで、tabi-log 側が実際に2件取りこぼした。
同じ構成の本プロジェクトでも起こりうるため、その再発防止として置く。

## 使い方

1. **apply の前に、この一覧を上から読む。** 「デプロイでしか検証できないもの」を
   先に用意しておく必要がある
2. apply 後、**上から順に潰す**
3. **設定を変えてしまう項目は、変える前に済ませる**（レート制限が該当）
4. すべて済ませてから destroy する

## 0. apply の前に用意しておくもの

| # | 用意するもの | 理由 |
|---|---|---|
| 0-1 | CD ワークフローと IAM | デプロイでしか検証できない。後から書くと、そのためだけにもう一度 apply することになる |
| 0-2 | 検証用の画像 | 画像アップロード経路の確認に使う |

## 1. 既定の設定でしか確認できないこと（**最優先。設定を変える前に**）

**計測のために上限を上げると、この経路は二度と踏めなくなる。**

レート制限は 2026-08-30 に入れたが（`docs/operations.md` 4章）、
**実環境で効くことを一度も確認していない。** 負荷計測のために上限を上げたためである。

| # | 確認すること | 手順 | 期待 |
|---|---|---|---|
| 1-1 | **X-Forwarded-For の段数が正しい** | 左端の XFF だけを変えて、ログインの上限（既定バースト10）を超えるまで試す | **429 が返る**。返らないなら左端を採っており、詐称で制限を回避できる |
| 1-2 | **利用者ごとに別々に数える** | 上限に達した状態で、別の経路から1回ログインする | **通る**。通らないなら全員が1つの鍵に潰れている |
| 1-3 | アカウント単位の制限 | 同じメールアドレスへ、異なる送信元から失敗を重ねる | 429 `TOO_MANY_LOGIN_ATTEMPTS` |
| 1-4 | 書き込みの上限 | 投稿を上限（既定バースト30）を超えて作る | 429 `RATE_LIMITED` |
| 1-5 | `Retry-After` | 429 の応答ヘッダ | 秒数が入っている |

> **1-1 と 1-2 は両方見ること。** 片方だけでは「制限が効いている」ことと
> 「正しい単位で効いている」ことを区別できない。

## 2. 失敗したときの動き

**成功経路だけ通して終わりにしない。**

| # | 確認すること | 期待 |
|---|---|---|
| 2-1 | 権限が無いとき | 403 が **JSON** で返る |
| 2-2 | 存在しないとき | 404 が **JSON** で返る |
| 2-3 | データベースが落ちたとき | `/api/livez` は 200 のまま、`/api/readyz` が 503 |
| 2-4 | 並行リフレッシュ | 2つのタブから同時にリフレッシュしても全ログアウトされない |
| 2-5 | 盗用検知 | 失効済みのリフレッシュトークンを猶予の外で再提示すると全トークンが失効する |

> **2-1 と 2-2 は tabi-log で実際に壊れていた。** CloudFront の
> `custom_error_response` が全ビヘイビアに効き、API のエラーまで
> 200 + HTML に化けていた。本プロジェクトは CloudFront Function 方式なので
> 同じ問題は無いはずだが、**確認はする。**
