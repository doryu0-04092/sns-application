# API設計

> **各エンドポイントの詳細な仕様(リクエスト/レスポンスのフィールド・型・制約)は Swagger UI で参照する。**
> アプリ起動後 <http://localhost:8080/swagger-ui.html> で開ける。Try it out でその場で実行もできる。
>
> 2つのドキュメントの役割分担:
>
> | | 扱うもの |
> |---|---|
> | **Swagger UI** (自動生成) | **何を**・**どんな型で** — パス、パラメータ、フィールドの型と制約、エラーコード |
> | **この文書** (手書き) | **なぜ** — 設計の方針、採用理由、v1での割り切り |
>
> 下のエンドポイント一覧は全体像を把握するための索引。**型の詳細は Swagger UI が正**。

## 基本方針

- REST + JSON。バックエンド(Spring Boot)がAPIを提供し、フロントエンド(React)が`fetch`経由で呼び出す。
- ベースURL: `http://localhost:8080/api`(ローカル開発時)
- 認証はhttpOnlyクッキーに格納したJWTで行う。フロントエンドからのリクエストは`credentials: include`で送信する。

## レスポンス規約

成功時:
```json
{ "data": { } }
```

エラー時:
```json
{ "error": { "code": "NOT_FOUND", "message": "投稿が見つかりません" } }
```

- 認証エラー: `401 Unauthorized`
- 権限エラー(他人の投稿を編集/削除しようとした等): `403 Forbidden`
- 存在しないリソース: `404 Not Found`
- バリデーションエラー(280文字超過等): `400 Bad Request`

## ページネーション

タイムラインとユーザー一覧・フォロー関係の一覧はカーソルベースページネーションを採用する
(コメント一覧は対象外。後述の「v1における簡略化」を参照)。

- リクエスト: `?cursor=<最後に取得した投稿のID>&limit=20`
- レスポンス: `{ "data": { "items": [...], "nextCursor": "123" } }`(`nextCursor`が`null`なら末尾)
- `limit`は1〜50に丸められる。範囲外を指定してもエラーにはならない
- タイムラインのみ`sinceId`も受け付ける。`cursor`が「これより古い」を意味するのに対し、
  `sinceId`は「これより新しい」を意味する(新着ポーリング用)

### 画像アップロード

画像本体はバックエンドを経由せず、ブラウザからS3へ直接アップロードする。バックエンドは署名付きURLを発行するだけで、大きなファイルでサーバーの帯域・タイムアウトがボトルネックになるのを避けている。

| メソッド | パス | 概要 | 認証要否 |
|---|---|---|---|
| POST | /api/uploads/presign | アップロード用の署名付きURLを発行する。`contentTypes`(ファイル数分の配列)を受け、`[{key, uploadUrl}]` を返す。キーはサーバー側でUUID採番するため、クライアントが任意のキーを指定して他人のオブジェクトを上書きすることはできない(F-05, F-14) | 要 |

アップロードの流れ:

1. `POST /api/uploads/presign` で `key` と `uploadUrl` を取得する
2. ブラウザが `uploadUrl` へ直接 `PUT` する(署名時と同じ `Content-Type` を送ること。異なるとS3が拒否する)
3. `POST /api/posts` または `PATCH /api/users/me` に `key` を渡す
4. バックエンドが `HeadObject` で実体(サイズ・形式)を検証し、正式な場所へ移動してからDBに登録する

## v1における簡略化(明示的な割り切り)

- 画像は投稿作成時にのみ添付可能とし、作成後の画像の追加・削除・並び替えAPIは設けない。
- 画像アップロードの制約: 投稿は最大4枚、1ファイルあたり最大5MB、対応形式はjpeg/png/webp/gifのみ。アイコン画像も同じ制約(枚数上限は1枚)。
- 画像は非公開のS3バケットに保存し、表示用URLはリクエストごとに署名して返す(有効期限24時間)。**DBに保存するのはURLではなくS3キー**であり、レスポンスに載せる直前に署名付きURLへ変換している。CloudFrontは今回のスコープ外。
- いいね・フォローは「作成(POST)」「解除(DELETE)」の2エンドポイントとし、トグル1本化はしない(DBのユニーク制約とAPIの意味を一致させるため)。
- コメント一覧は`GET /api/posts/{postId}/comments`で常に全件を返す方針とし、コメント自体のページネーションは初期スコープでは設けない(コメント数が増えた場合は将来検討)。返却はネスト構造ではなく`parentCommentId`を持つ平坦な配列とし、ツリーの組み立てはクライアントに任せる(サーバー側で入れ子のDTOを組む処理を持たずに済むため)。
- 論理削除された投稿・コメントは、ぶら下がるコメント/返信がある場合に限りツームストーンとして残す(`deleted: true`・本文はnull)。ぶら下がりが無ければ一覧からも詳細からも消える。この可視性ルールは`TombstoneVisibilityTest`で固定している。
