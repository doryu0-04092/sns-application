# 運用設計

障害が起きたときに **何が起きたかを追えること** を目的に、ログの出し方・監視する項目・障害時の動き方をまとめる。

ログのありがたみは平常時には感じられない。だが必要になるのはトラブルのときで、
その時点でログが無ければ手の打ちようがない（サーバーを再起動してログが消えていれば、原因究明は不可能になる）。
そのため「入れるかどうか」は判断の対象にせず、最初から入れる前提で設計している。

## 1. ログ設計

### 1.1 出力形式と出力先

出力先は **標準出力(stdout)のみ**。アプリケーションはファイルにも外部サービスにも直接書かない。
収集はコンテナ基盤の責任とし、アプリは「送り先を知らない」状態を保つ。
こうしておくと、収集先を Datadog / CloudWatch Logs / Grafana Loki のどれに変えてもアプリの変更は要らない。

形式は Spring のプロファイルで切り替える（設定: [backend/src/main/resources/logback-spring.xml](../backend/src/main/resources/logback-spring.xml)）。

| プロファイル | 形式 | ログレベル | 用途 |
|---|---|---|---|
| 既定（`mvn spring-boot:run`・テスト） | 人が読める1行テキスト | ルート INFO / `com.snsapp.backend` は DEBUG | ローカル開発。調査に必要な自作コードの詳細だけを出す |
| `docker`（`docker compose up`・本番相当） | JSON 1行 | INFO | 収集エージェントに読ませる。**DEBUG は出さない** |

**本番で DEBUG を出さない理由**: 書き込みは物理的に遅く、量も桁違いに増える。
全てを出す設計にすると1日あたり数GB規模になり、ディスクと転送量を圧迫したうえに肝心のログが埋もれる。

### 1.2 JSON のフィールド

```json
{
  "timestamp": "2026-08-10T07:03:11.311409336Z",
  "level": "INFO",
  "logger": "com.snsapp.backend.service.AuthService",
  "thread": "http-nio-8080-exec-7",
  "message": "user signed up userId=7",
  "requestId": "0416a3aa-2a45-4d46-8571-291191c2cfbe",
  "userId": 7,
  "service": "sns-backend"
}
```

| フィールド | 意味 |
|---|---|
| `timestamp` | 発生時刻（UTC） |
| `level` | ログレベル（1.3参照） |
| `logger` | 出力元クラス。どのコードが出したか |
| `thread` | 処理スレッド |
| `message` | 本文 |
| `requestId` | **リクエスト単位の追跡ID**（1.4参照） |
| `userId` | 認証済みリクエストの利用者ID |
| `service` | 発生元サービス名。複数サービスのログを1箇所へ集めたときの識別に使う |
| `stack_trace` | 例外発生時のみ |
| その他 | アクセスログの `method` / `path` / `status` / `durationMs` など、出力箇所ごとの追加項目 |

構造化しておくのは、監視ツール側で「ステータスが500のものだけ」「特定利用者のものだけ」といった
絞り込みや集計ができるようにするため。テキストのままでは検索しかできず、集計・可視化に載せられない。

### 1.3 ログレベルの使い分け

| レベル | 意味 | このアプリでの例 |
|---|---|---|
| **ERROR** | 即時対応が必要 | 想定外の例外（DB接続不可、NPE等）。`GlobalExceptionHandler` の catch-all |
| **WARN** | 今は動いているが、放置すると問題になりうる | S3のオブジェクト削除失敗、405（クライアント実装の誤りの兆候） |
| **INFO** | 業務上重要な出来事 | ユーザー登録・ログイン・投稿の作成/削除、アクセスログ、想定内の業務エラー |
| **DEBUG** | 開発・調査用の詳細 | 入力バリデーション違反、存在しないパスへのアクセス、ヘルスチェックのアクセスログ |

**WARN の扱いに注意**: 「警告だから大丈夫」と放置されやすい。増加傾向にあるWARNは
ERRORの前触れであることが多いため、2節の監視項目で件数の推移を見る。

**INFO を業務イベントに出す理由**: 「登録はできたのにログインできない」といった問い合わせで、
**どこまで成功したか** を切り分けられる。登録完了のINFOがあれば、原因を登録処理ではなく
認証側に絞り込める。

### 1.4 リクエストの追跡（requestId）

複数の利用者のリクエストが同時に処理されるため、追跡IDが無いと
「このエラーログはどのリクエストのものか」を判別できない。

[RequestLoggingFilter](../backend/src/main/java/com/snsapp/backend/logging/RequestLoggingFilter.java) が
全リクエストの入口でUUIDを発行し、

- ログ出力コンテキスト（MDC）に載せる → **そのリクエスト中に出る全てのログに自動で付く**
- レスポンスヘッダー `X-Request-Id` で返す → 利用者からの問い合わせと突き合わせられる

**保守上の注意**: このフィルタは全フィルタの最外周に登録する必要がある
（内側に置くと認証エラー401がアクセスログに残らない）。また、処理後の MDC クリアは必須で、
怠るとスレッドの使い回しにより別リクエストのログへ前の追跡IDが混ざる。

### 1.5 ログに出さないもの

一度ログに残った情報は取り消せない。以下は **出力してはならない**。

- パスワード、パスワードハッシュ
- 認証トークン（JWT）、Cookie、`Authorization` ヘッダー
- メールアドレスなど、本人を特定できる情報
- 投稿本文などの利用者が書いた内容
- リクエストボディ、クエリ文字列

**マスキング処理で後から消すのではなく、そもそも渡さない設計にしている**。
アクセスログはメタデータ（メソッド・パス・ステータス・所要時間）のみを扱い、
ヘッダー・Cookie・ボディ・クエリ文字列を受け取る経路自体を作っていない。
マスキングは「消し忘れ」で漏れるが、渡さない設計なら漏れる経路が存在しない。

利用者の識別には ID のみを使う（`userId=7`）。

## 2. 監視項目と閾値

対象は **このWebアプリケーションに関する指標** のみ。
インフラ層（CPU・メモリ・ディスク使用率、コンテナ再起動回数）は現状デプロイ先が未定のため対象外とする。

重要度は「どれだけ早く人が動くべきか」で決める。

| 重要度 | 対応期限 | 通知手段（想定） |
|---|---|---|
| **Critical** | 即時 | 電話・オンコール |
| **High** | 30分以内に確認 | チャット（Slack等）へのメンション |
| **Warning** | 営業時間内に確認 | チャットへの通知（メンションなし） |
| **Info** | 対応不要 | 記録のみ |

### 監視項目

| # | 項目 | データ元 | 閾値 | 重要度 | 見る理由 |
|---|---|---|---|---|---|
| 1 | 5xx エラー率 | アクセスログの `status` | 5分間で 10% を超える | Critical | サービスが利用者に対して機能していない状態 |
| 2 | ERROR ログ件数 | `level=ERROR` | 5分間で 10件を超える | Critical | 想定外の例外。1件でも原因究明の対象だが、急増は障害を意味する |
| 3 | レイテンシ P99 | アクセスログの `durationMs` | 10分間 2秒を超える | High | 応答が返っていても実質使えない状態。DB遅延の兆候 |
| 3' | レイテンシ P99（予兆） | アクセスログの `durationMs` | 10分間 500ms を超える | Warning | 平常時の実測は 18ms。500ms は 27倍で明らかに異常だが、まだ手遅れではない段階 |
| 4 | 4xx エラー率 | アクセスログの `status` | 5分間で 30% を超える | Warning | 通常はクライアント側の問題だが、急増は不正アクセスの探索や API の破壊的変更を示す |
| 5 | 401 の急増 | `status=401` | 5分間で 50件を超える | Warning | 認証情報の総当たり試行の兆候 |
| 6 | WARN ログ件数 | `level=WARN` | 前日同時刻比で 3倍 | Warning | ERROR の前触れ。傾向として見る |
| 7 | ログの途絶 | 全ログ | 10分間 1件も届かない | Critical | アプリ停止、またはログ収集経路の断絶。**「異常が無い」と区別がつかないため必ず監視する** |
| 8 | ユーザー登録数/時 | `user signed up` の件数 | 前週同曜日比で 50% を下回る | Warning | 技術的には正常でも登録導線が壊れている場合がある（業務指標） |
| 9 | 投稿作成数/時 | `post created` の件数 | 前週同曜日比で 50% を下回る | Warning | 同上。サービスの主機能が使われているかの確認 |

閾値は運用開始時の暫定値。実際のトラフィックを見て見直す。
**対応不要のアラートが鳴り続ける状態は、鳴っても誰も見なくなるため最も危険**。
鳴りっぱなしの項目は閾値を上げるか Info へ落とす。

### レイテンシの閾値を 3秒 から 2秒 + 500ms(予兆) に変更した理由

当初の「P99 3秒超」は実測に基づかない値だった。
[パフォーマンステスト](perf-test-report.md) で実際に測ったところ、**この閾値では飽和を検知できない**ことが分かった。

| 状態 | 実測 P99 | 旧閾値(3秒)で鳴るか |
|---|---|---|
| 平常時（投稿2万件・VU50） | 18 ms | 鳴らない |
| データ5倍（投稿10万件・VU50） | 587 ms | 鳴らない |
| **完全飽和**（PostgreSQL の CPU が100%に張り付いた状態） | **1.58 秒** | **鳴らない** |

このアプリは過負荷時にエラーを返さず、キューイングで吸収する設計になっている
（レポート 6-3）。そのため応答は遅くなる一方でエラーにはならず、
**P99 が 3秒に達する頃には既に手遅れ**である。

平常時が 18ms であることを踏まえ、次のように置き直した。

- **500ms（Warning）**: 平常時の27倍。明らかに異常だが、まだ対処できる段階
- **2秒（High）**: 完全飽和時の実測 1.58秒 を上回る水準。ここまで来たら即座に対応する

### 追加すべき監視項目（メトリクス基盤の導入が前提）

飽和テストでは、**応答時間が目に見えて劣化する前に**次の2つが先に限界へ達していた。
レイテンシは結果であり、これらは原因側の先行指標である。

| # | 項目 | 閾値（提案） | 重要度 | 根拠 |
|---|---|---|---|---|
| M-1 | DB の CPU 使用率 | 5分間 80% を超える | Warning | 飽和の直接の原因。実測では上限200%(2コア)に対し 197〜203% で張り付いた |
| M-2 | コネクションプール使用率 | プール上限の80%超が5分継続 | Warning | 飽和時に同時アクティブ接続がプール上限(10)に張り付いた |

ただし**現状はメトリクスの収集基盤が無い**（4章「現状の実装範囲と今後」を参照）。
この2項目を実現するには `spring-boot-starter-actuator` + Micrometer の導入が前提になる。

なお **アプリ側の CPU 使用率は単独では監視指標にならない。**
飽和時も 48〜55%（上限2コアに対し）にとどまっており、
これを見てスケールアウトを判断すると、DBが飽和していても反応しない。

### ダッシュボードの推奨構成

監視ツールを入れたときに、どの画面を用意するかの設計。
**1画面に全部を詰め込まない**。見る目的（今壊れているか／傾向はどうか／原因はどこか）で画面を分ける。

#### 画面1: サービス健全性（障害時に最初に開く）

「今、利用者から見てサービスは動いているか」を10秒で判断するための画面。

| パネル | 内容 | データ元 |
|---|---|---|
| 稼働状況 | 直近5分のログ受信有無（単一の数値。0なら赤） | 全ログの件数 |
| ステータス別リクエスト数 | 2xx / 4xx / 5xx を色分けした積み上げ時系列 | アクセスログの `status` |
| エラー率 | 5xx の割合（%）。閾値10%に赤線を引く | 同上 |
| レイテンシ | P50 / P95 / P99 の3本の折れ線 | アクセスログの `durationMs` |
| 直近のERRORログ | 最新20件のログ一覧（`requestId` をクリックできる形に） | `level=ERROR` |

#### 画面2: エラー分析（原因の当たりをつける）

| パネル | 内容 |
|---|---|
| エラーコード別の件数 | `api error` の `code` 別に集計。どの業務エラーが増えたかが分かる |
| エンドポイント別 5xx | `path` 別の5xx件数。特定の機能だけ壊れているのか全体かを切り分ける |
| ログレベル別の推移 | ERROR / WARN / INFO の件数を時系列で。WARNの増加傾向を早期に掴む |
| 例外クラス別 | `logger` と `stack_trace` の先頭行で集計。同じ原因の再発を見つける |
| 401 / 403 の推移 | 認証・認可エラー。急増は総当たり試行や権限設定ミスの兆候 |

#### 画面3: 利用状況（ビジネス指標）

技術的には正常でも、利用者が使えていない状態を見つけるための画面。

| パネル | 内容 |
|---|---|
| ユーザー登録数 / 時 | `user signed up` の件数 |
| ログイン数 / 時 | `user logged in` の件数 |
| 投稿・コメント作成数 / 時 | `post created` / `comment created` の件数 |
| フォロー数 / 時 | `user followed` の件数 |
| アクティブ利用者数 | アクセスログの `userId` のユニーク数 |

#### 共通の設計方針

- **時間範囲は画面全体で連動させる**（1つのパネルで期間を変えたら全部が追従する）。障害調査では複数の指標を同じ時刻で見比べるため。
- **閾値は線として描く**。数値だけだと「高いのかどうか」が読み手の記憶に依存する。
- **ログのパネルからは `requestId` で詳細へ飛べるようにする**。ダッシュボードは異常の発見までが役割で、原因特定はログの絞り込みで行う。
- **画面1は常時表示に耐える密度にする**。パネルを増やしすぎると異常に気づけなくなる。

### 通知の設定状況

**現時点でアラートの実通知先は設定していない**。監視ツール（Datadog 等）を未導入で、
通知先となるチャットや電話の運用体制も無いため。上表は導入時にそのまま設定へ落とせる形で定義したもの。

構造化ログを stdout に出す形にしてあるため、収集エージェントを追加すれば
アプリ側を変更せずに監視ツールへ接続できる。

## 3. 障害対応フロー

```
検知 → 影響範囲の確認 → 原因の特定 → 対処（修正 or 切り戻し） → 振り返り
```

### 3.1 検知

アラート（2節）、または利用者からの問い合わせ。
問い合わせの場合は、可能なら **`X-Request-Id` の値を聞く**。これがあれば該当リクエストのログへ直接辿れる。

### 3.2 影響範囲の確認

「一人だけの問題か、全体の障害か」をまず切り分ける。5xx エラー率（項目1）と
ERROR ログ件数（項目2）が上がっていなければ、特定の利用者・特定の操作に限った問題である可能性が高い。

### 3.3 原因の特定

ローカル環境（`docker compose up`）での調査例。監視ツール導入後は同じ条件をツール側の検索で指定する。

```bash
# ERROR ログだけを見る
docker compose logs backend --no-log-prefix | grep '"level":"ERROR"'

# 特定のリクエストに関わるログを時系列で全て追う（アクセスログ・業務ログ・例外が揃う）
docker compose logs backend --no-log-prefix | grep '0416a3aa-2a45-4d46-8571-291191c2cfbe'

# 500 を返したリクエストを洗い出す
docker compose logs backend --no-log-prefix | grep '"status":500'

# 特定利用者の操作を追う
docker compose logs backend --no-log-prefix | grep '"userId":7'
```

`requestId` で絞り込めば、そのリクエストの **アクセスログ・業務イベント・スタックトレースが一続きで揃う**。
ここが追跡IDを入れている理由そのものになる。

原因が特定できない場合は、`docker` プロファイルを外して（またはログレベルを DEBUG へ下げて）再現させる。
バリデーション違反や404など、本番では抑制している詳細が見えるようになる。

### 3.4 対処

- 原因が直近のリリースにある場合は **まず切り戻す**。修正を当てるのはその後でよい。
- データ不整合を伴う場合は、修正前に影響範囲（対象レコード）を特定して記録しておく。

### 3.5 振り返り（ポストモーテム）

対応後、以下を文書として残す。目的は個人の責任追及ではなく、同じ障害を繰り返さないこと。

- 何が起きたか（事象・影響範囲・継続時間）
- なぜ起きたか（技術的な原因と、それを見逃した仕組みの側の原因）
- どう気づいたか（アラートで気づけたか、利用者からの指摘だったか）
- 再発防止として何を変えるか（コード・テスト・監視項目・閾値）

**「アラートで気づけなかった」場合は、監視項目そのものの不足を意味する**。2節へ項目を追加する。

## 4. 現状の実装範囲と今後

| 監視の3本柱 | 内容 | 現状 |
|---|---|---|
| **ログ** | 何が起きたか | **実装済み**（構造化JSON・追跡ID・アクセスログ・業務イベント） |
| **メトリクス** | 数値の推移 | 未実装。ログから集計する形でしか見られない |
| **トレース** | 処理の流れ | 未実装（単一サービス構成のため、requestId による相関で当面は足りる） |

3つが揃って初めて「異常が一時的なものか、悪化し続けているのか」を判断できる。
現状はログのみのため、判断の材料としては不足している。

**次に入れるならメトリクス**。ログが「個別の出来事の記録」であるのに対し、
メトリクスは「システムの状態の時系列」であり、メモリ使用量の緩やかな増加のように
**ログには一切現れない異常** を捉えられる。
Spring Boot Actuator + Micrometer + Prometheus を追加すれば、
2節の監視項目のうち 1・3（エラー率・レイテンシ）をログの集計ではなく直接の指標として扱える。
