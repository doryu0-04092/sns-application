## 0. 先に読むべき前提 — この数字が何を保証し、何を保証しないか

**この測定はローカルPC1台の上で行った。したがって応答時間の絶対値は本番環境の性能保証にならない。**

計測する側(k6)と計測される側(Docker上のアプリとDB)が同じPCのCPUを分け合っており、
Docker Desktop on Windows は WSL2 を経由するためファイルI/Oも実機と異なる。
さらに、そもそも比較対象となる本番環境が存在しない。[技術スタック](tech-stack.md) の
「AWS移行の状況」にある通り、ECS・RDS・ALB のいずれも未定義であり、
S3 と IAM も現時点では destroy 済みである。

したがって本レポートの数字は次のように読むこと。


| 読み方           | 可否      | 例                         |
| ------------- | ------- | ------------------------- |
| エンドポイント間の相対比較 | **できる** | 「フォロー中フィードは全体フィードより18%遅い」 |
| データ量に対する劣化の傾向 | **できる** | 「コメント500件の投稿は数件の投稿の何倍か」   |
| 壊れ方の質         | **できる** | 「飽和したときエラーを返すか、無限に待つか」    |
| 設定の妥当性        | **できる** | 「コネクションプールが上限に届くか」        |
| 応答時間の絶対値      | できない    | 「本番でも15msで返る」とは言えない       |
| 同時接続数の上限      | できない    | 「本番でもVU300に耐える」とは言えない     |


「VU300まで耐えた」を「本番でも300同時接続をさばける」と読み替えるのは誤りである。
本番環境が決まった時点で、`BASE_URL` を差し替えて同じシナリオを再実行し、本レポートと突き合わせること。

### 実施したこと・しなかったこと


| 種別        | 実施           | 内容                                           |
| --------- | ------------ | -------------------------------------------- |
| 負荷テスト     | 済            | 6シナリオ、VU 10→50、各3分                           |
| ストレステスト   | 済            | VU 50→300、壊れるまで上げて回復を観測                      |

| 投入直後 | 501   | 20,000 | 61,500   | 100,000 | 30,000        | 10,000  |

### 目標値が閾値として機能しなかった

**P-1 の目標 500ms に対し実測 15.41ms。32倍の余裕がある。** 他も同様で、

これは目標値の置き方の失敗である。実測値を知らない状態で「ユーザーが待たされたと感じる境界」から

**実測に基づく現実的な閾値への置き換えを 8章で提案する。**

### ログインだけが桁違いに遅い

`POST /auth/login` の p95 は 696ms で、フィード取得の45倍である。
原因は BCrypt(cost 10)で、これは**意図的に遅く作られたアルゴリズムなので設計通りの挙動**であり、
不具合ではない。avg 164ms に対し p95 696ms と分布が大きく歪んでいるのは、
2コアに対し50VUが同時にハッシュ計算を要求し、CPU待ちの行列ができるためである。

意味があるのは「遅い」ことではなく、**ログインのスループット上限を決めるのが
DBでもネットワークでもなくCPUである**という事実である。11章でAWS構成の材料として扱う。

なお `search` の全体 p99 が 54.40ms と跳ねているが、これは各VUの初回イテレーションで走る
ログインが混ざったもので、`GET /users?q=` 単体では p99 6.44ms である。
エンドポイント別のタグを付けていなければ、この数字を「検索が遅い」と誤読していた。

## 5. ボトルネックの特定

負荷・スパイク・耐久のいずれもエラー0件・p95 20ms以下で通過した。
つまり**このデータ量・この負荷では、性能上の問題は表面化しない。**

そこで「どこが最初に苦しくなるか」をクエリ単位まで下ろして調べた。
以下はすべて `pg_stat_statements` と `EXPLAIN (ANALYZE, BUFFERS)` の出力に基づく。

### 5-1. 最大の発見: `likes` / `comment_likes` に `user_id` の索引が無く、毎回全件走査している

`pg_stat_statements` のテーブル別統計で、`likes` **に対する順次走査が13,160回、
累計13億行(1,315,660,483行)の読み取り**が記録されていた。
1回あたり平均99,974行、つまり毎回テーブル全体を読んでいる。


| テーブル          | 行数     | seq_scan回数 | seq_tup_read      | 1回あたり       |
| ------------- | ------ | ---------- | ----------------- | ----------- |
| **likes**     | 99,996 | **13,160** | **1,315,660,483** | **99,974行** |
| users         | 501    | 5,982      | 2,991,974         | 500行        |
| comment_likes | 30,000 | 39         | 1,080,000         | 27,692行     |


原因はフィード取得の `EXPLAIN` で特定できた。

```
Limit (actual time=3.025..3.079 rows=20)
  ...
  SubPlan 4                                       <- like_count
    ->  Index Only Scan using idx_likes_post_id on likes l
          (actual time=0.001..0.001 rows=0 loops=20)
  SubPlan 8                                       <- is_liked
    ->  Seq Scan on likes l_1 (actual time=2.931..2.931 rows=0 loops=1)
          Filter: (user_id = 2)
          Rows Removed by Filter: 99996
          Buffers: shared hit=745
Execution Time: 3.260 ms
```

**実行時間 3.260ms のうち 2.931ms(90%)を** `SubPlan 8` **だけが占めている。**

`SubPlan 8` は `is_liked` の判定である。

```sql
EXISTS (SELECT 1 FROM likes l WHERE l.post_id = p.id AND l.user_id = #{currentUserId})
```

`likes` の索引は次の3つしか無い(`V3__add_posts_comments_likes_follows.sql`)。


| 索引                                   | 列                    |
| ------------------------------------ | -------------------- |
| `likes_pkey`                         | `id`                 |
| `likes_post_id_user_id_key` (UNIQUE) | `post_id`, `user_id` |
| `idx_likes_post_id`                  | `post_id`            |


`user_id` **を先頭に持つ索引が1つも無い。** 複合索引 `(post_id, user_id)` は
先頭列が `post_id` なので `user_id = ?` 単独の絞り込みには使えない。
そのためプランナは「このユーザーのいいね全部」をハッシュ化する計画を選び、
`likes` テーブル全体を走査する。

同じ問題がコメント取得にもある。

```
SubPlan 5                                         <- コメントの is_liked
  ->  Seq Scan on comment_likes cl_1 (actual time=0.853..0.853 rows=0 loops=1)
        Filter: (user_id = 2)
        Rows Removed by Filter: 30000
Execution Time: 1.770 ms
```

こちらは実行時間 1.770ms のうち 0.853ms(48%)を占める。

#### 重要な性質: 表示件数ではなくテーブル全体のサイズに比例する

`LIMIT 20` を付けても `SubPlan 8` は `loops=1` で1回だけ走り、
そのたびに `likes` 全件を読む。つまり**1ページに何件表示するかとは無関係に、
サービス全体のいいね総数に比例して重くなる。**

現在10万件で2.9ms。単純比例なら100万件で約29ms、1000万件で約290msになる。
これは「今は速いが、いいねが増えるほど確実に効いてくる」という性質であり、
放置すると後から効いてくる種類の問題である。

#### 修正の効果を実測した

計測用DBに索引を2本追加し、同じクエリの実行計画を比較した(比較後に索引は削除して元に戻した)。

```sql
CREATE INDEX idx_likes_user_id ON likes (user_id, post_id);
CREATE INDEX idx_comment_likes_user_id ON comment_likes (user_id, comment_id);
```


|     | 該当サブクエリの実行計画                              | サブクエリ時間 | クエリ全体の実行時間   |
| --- | ----------------------------------------- | ------- | ------------ |
| 追加前 | `Seq Scan on likes` (99,996行を走査)          | 2.942ms | **3.202 ms** |
| 追加後 | `Index Only Scan using idx_likes_user_id` | 0.042ms | **0.195 ms** |


**クエリ全体で16.4倍、該当サブクエリ単体では70倍速くなった。**

`(user_id, post_id)` の複合にしているのは、`post_id` も条件に含まれるため
`Index Only Scan`(テーブル本体を読まずに索引だけで完結する)になるからである。
`user_id` 単独の索引でも改善するが、索引からテーブルへの参照が1回増える。

### 5-2. 事前に疑っていた3点は、いずれも実測ではボトルネックではなかった

計測前にコードを読んで挙げた懸念のうち、3つは支持されなかった。
**測る前に直していたら、効果の無い変更に時間を使うところだった。**


| 事前の懸念                                   | 実測                                                                                            | 評価                                                |
| --------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 1投稿ごとに相関サブクエリが5本走る                      | `SubPlan 3`(comment_count) `4`(like_count) `6`(is_following) はいずれも `loops=20` で **0.001ms/回** | **問題なし。** 索引が効いている。重いのは索引の無い `SubPlan 8` だけ       |
| `comment_count` が二重ネスト(EXISTSの中にEXISTS) | 内側の `SubPlan 1` は `never executed`                                                            | **問題なし。** 短絡評価で内側まで到達していない                        |
| コメント一覧が LIMIT なしの全件取得                   | 502件の per-row サブクエリは `loops=502` で **0.000ms/回**。p95 は 502件で7.85ms、3件で3.74ms                  | **DB時間としては問題なし。** データ量167倍に対し2.1倍。ただし別の問題がある(5-3) |
| `display_name` への索引なし両端ワイルドカード `ILIKE`  | `Seq Scan on users`(501行)で p95 4.70ms                                                         | **この規模では問題なし。** 501行の全件走査は誤差。ユーザー数が桁違いに増えて初めて効く   |


`posts` の `created_at` / `deleted_at` に索引が無い点も、
`ORDER BY p.id DESC` が主キー索引の逆順走査で足りているため問題にならなかった
(`Index Scan Backward using posts_pkey`)。

### 5-3. HTTPレスポンス圧縮が無効

コメント全件取得のDB時間は問題なかったが、**転送量には明確な問題があった。**


| レスポンス                                  | 実測サイズ                    | gzip圧縮後          | 削減率       |
| -------------------------------------- | ------------------------ | ---------------- | --------- |
| `GET /posts/20011/comments` (コメント502件) | **167,136 B (163.2 KB)** | 8,266 B (8.1 KB) | **95.1%** |
| `GET /posts?feed=all&limit=20`         | 7,435 B (7.3 KB)         | 761 B (0.7 KB)   | **89.8%** |


`Accept-Encoding: gzip` を付けて要求しても、レスポンスに `Content-Encoding` ヘッダが無く、
サイズも変わらない。`server.compression` の設定はリポジトリのどこにも存在せず、
**Spring Boot の既定(無効)のまま**である。

これは**コードを読んでも見つからない種類の問題**である。
「存在しない設定」は検索できないため、実際にレスポンスを見るまで気づけない。

コメント一覧にページングが無いこと自体は、DB負荷の観点では問題にならなかったが、
**1リクエストで163KBを無圧縮で送る**という点では実害がある。
圧縮を有効にすれば 8.1KB になり、ページング導入より先に効く。

### 5-4. ログインのコストはBCryptが支配している

`POST /auth/login` の p95 は 696ms で、他のエンドポイントの40〜100倍である。
これは BCrypt(cost 10)によるもので、意図的に遅く設計されたアルゴリズムなので
**それ自体は正しい挙動**である。

重要なのは、これが**DBでもネットワークでもなくCPUで決まる**という点である。
飽和テストでは、事前認証によってログインを測定から除外して初めて
DB側の飽和点が観測できた。裏を返せば、**ログインが多い時間帯には
CPUがそちらに取られ、他のリクエストの処理能力が下がる。**
11章でAWS構成の材料として扱う。

### 6-3. 飽和時の壊れ方 — キューイングによる緩やかな劣化

**このアプリはエラーを返さない。遅くなるだけで、すべて処理し切る。**


|               | 平常時(負荷テスト) | 飽和時             |
| ------------- | ---------- | --------------- |
| p95           | 15.4ms     | **1.20s (78倍)** |
| エラー率          | 0.00%      | **0.00%**       |
| 個々のクエリの最長実行時間 | 0.0s       | **0.0s**        |


`max_query_sec` が全区間 0.0 であることが決定的である。
**遅延はDBのクエリが遅くなったのではなく、順番待ちの行列で発生している。**
`db_active` がプール上限の10に張り付いていることから、
待ち行列の場所は HikariCP のコネクション取得待ちだと特定できる。

これは設計として妥当な挙動である。過負荷時にリクエストを捨てず、
データも失わず、負荷が引けば即座に回復する(観測終了直後のサンプルで postgres CPU は 0.0%)。

**合格条件 B-1 の判定:**


| 条件          | 結果                                          |
| ----------- | ------------------------------------------- |
| ハングしない      | **満たす**                                     |
| 無限に待たない     | **満たす**(最長 2.91s)                           |
| プロセスが死なない   | **満たす**                                     |
| 負荷を戻せば性能が戻る | **満たす**(6-1 で確認: VU300→50 で CPU 166%→37.6%) |
| エラーを返す      | **満たさない** — が、エラーを返さずに処理し切る方が望ましいため問題としない   |


**総合: 合格。** ただし合格条件の書き方に不備があった。
「エラーを返して回復する」は「ハングするよりマシ」という意図だったが、
実際にはそれより望ましい第3の挙動(キューイングで吸収)が存在した。
条件は「エラーを返すこと」ではなく「**有界な時間内に応答を返し、負荷が引けば回復すること**」と書くべきだった。

### 6-4. ただし、この先の挙動は未検証

VU500・418req/s でも p95 1.2s に留まり、**バックプレッシャ(過負荷時に受付を拒否する仕組み)が
働く水準には到達していない。** さらに負荷を上げ続けた場合、待ち行列が伸び続けて
HikariCP の `connection-timeout`(既定30秒)に到達し、そこで初めてエラーが出るはずだが、
**その水準は今回確認していない。**

つまり「壊れ方」は分かったが「壊れる点」はまだ分かっていない。
本番構成が決まった時点で、その構成に対して同じ探索を行う必要がある。

### 6-5. 既存の監視閾値では、この飽和を検知できない

[運用設計](operations.md) の監視項目は「レイテンシ P99 が10分間3秒超で High」である。

**飽和時の実測 p99 は 1.58s で、この閾値を超えない。**
つまり PostgreSQL の CPU が100%に張り付き、応答が平常時の78倍に劣化しても、
**現在の監視設定ではアラートが上がらない。**

閾値の見直しを 8章で提案する。

### 7-3. 1画面の表示に6本のAPIを呼んでいる

`/home` の表示で発生したAPI呼び出しを時系列で並べる。

| `GET /auth/me`                          | 572 ms   | 191 ms |

| `GET /posts?feed=all&limit=20`          | 795 ms   | 188 ms |
| `GET /posts?feed=following&limit=20`    | 801 ms   | 196 ms |
| `GET /posts?feed=all&sinceId=...`       | 1,052 ms | 194 ms |
| `GET /posts?feed=following&sinceId=...` | 1,143 ms | 189 ms |


**問題が3つある。**

1. `GET /auth/me` **が2回呼ばれている。** 同時ではなく、1回目の完了後に2回目が走っている。

## 8. データ量を5倍にしたときの劣化 — 最も重要な結果

中データ(投稿2万件)では全エンドポイントが p95 20ms以下で、問題は表面化しなかった。
そこで**データ量を5倍にして同じ計測を繰り返し、劣化の仕方を見た。**


|     | users | posts   | comments | likes   | comment_likes | follows |
| --- | ----- | ------- | -------- | ------- | ------------- | ------- |
| 中   | 501   | 20,000  | 61,500   | 100,000 | 30,000        | 10,000  |
| 大   | 5,001 | 100,000 | 301,500  | 500,000 | 150,000       | 100,000 |
| 倍率  | 10x   | 5x      | 5x       | 5x      | 5x            | 10x     |


負荷条件は中データ時とまったく同じ(VU 10→50、3分、待ち時間1秒)。

### 8-1. 結果: フィード取得だけが突出して悪化した


| エンドポイント                              | 中データ p95     | 大データ p95      | 倍率        |
| ------------------------------------ | ------------ | ------------- | --------- |
| `GET /posts?feed=all`                | **15.41 ms** | **394.20 ms** | **25.6倍** |
| `GET /posts?feed=all` **(p99)**      | **18.34 ms** | **587.03 ms** | **32.0倍** |
| `GET /posts/{id}`                    | 5.31 ms      | 5.05 ms       | 0.95倍     |
| `GET /posts/{id}/comments`(通常)       | 3.74 ms      | 3.22 ms       | 0.86倍     |
| `GET /posts/{id}/comments`(**502件**) | 7.85 ms      | 7.46 ms       | 0.95倍     |
| `GET /users?q=`                      | 4.70 ms      | 5.13 ms       | 1.09倍     |


**フィード取得だけが25.6倍に悪化し、他はすべて横ばい。**
エラーは全シナリオで0件のままだった。

この対比が重要である。もし「相関サブクエリが多いこと」自体が問題なら、
同じくサブクエリを持つコメント取得も悪化するはずだが、そうなっていない。
**問題はサブクエリの本数ではなく、索引の無い1本に限定される。**

### 8-2. 検索は10倍にしても悪化しなかった

ユーザー数を 501 → 5,001 と10倍にしたが、`GET /users?q=` の p95 は
4.70ms → 5.13ms(1.09倍)でほぼ変わらなかった。

索引の無い列への両端ワイルドカード `ILIKE` は確かに全件走査になるが、
**5,000行の走査はまだ誤差の範囲**である。この設計が問題になるのは
さらに桁が変わってからで、現時点で索引を追加する根拠は無い。

### 8-3. 超線形に悪化した理由 — 並列スキャンへの切り替え

データは5倍にしかしていないのに、応答時間は25.6倍になった。
単純比例ではない。実行計画を比較すると理由が分かる。

**中データ(likes 10万件)**

```
SubPlan 8
  ->  Seq Scan on likes l_1 (actual time=2.931..2.931 rows=0 loops=1)
        Rows Removed by Filter: 99996
Execution Time: 3.260 ms
```

**大データ(likes 50万件)**

```
SubPlan
  Workers Planned: 2
  Workers Launched: 2
  ->  Parallel Seq Scan on likes l_1 (actual time=0.220..6.280 rows=33 loops=3)
        Rows Removed by Filter: 166632
Execution Time: 11.052 ms
```

テーブルが大きくなったことで、**PostgreSQL が並列スキャンに切り替えた。**
`Workers Launched: 2` かつ `loops=3`(リーダー + ワーカー2)で、
1リクエストあたり **3つのCPUワーカー** が動く。

つまりデータが5倍になったとき、起きたことは2つある。

1. 1回のスキャンで読む行数が5倍になった
2. **1リクエストが消費するCPUが3倍になった**

backend の PostgreSQL には2コアしか与えていない。そこに50VUが同時に
「3ワーカー分のCPU」を要求すれば、CPUは大幅な供給不足になる。
**個々のクエリが遅くなった以上に、待ち行列が伸びたことが25.6倍の正体である。**

### 8-4. 索引を追加した場合の効果(大データ)

同じデータに対して索引を2本追加し、実行計画を比較した。


|     | 該当サブクエリの実行計画                               | クエリ全体の実行時間    |
| --- | ------------------------------------------ | ------------- |
| 追加前 | `Parallel Seq Scan on likes`(ワーカー2 + リーダー) | **11.052 ms** |
| 追加後 | `Index Only Scan using idx_likes_user_id`  | **0.283 ms**  |


**39倍速くなった。** 中データでの16.4倍より効果が大きい。
データが増えるほど索引の有無の差は開くため、これは当然の結果である。

並列ワーカーが不要になることで、**1リクエストあたりのCPU消費が1/3になる**点も大きい。
応答時間の改善だけでなく、同じCPUで捌けるリクエスト数が増える。

### 8-5. 索引を追加して負荷テストを再実行した — 80倍速くなった

実行計画の比較(8-4)だけでは「クエリ単体が速くなる」ことしか言えない。
**同じ大データ・同じ負荷条件(VU 10→50、3分、待ち時間1秒)で
負荷テストそのものを再実行した。**


|          | `GET /posts?feed=all` p95 | p99         | 3分間のリクエスト数 |
| -------- | ------------------------- | ----------- | ---------- |
| 索引なし     | **394.20 ms**             | 587.03 ms   | 9,556      |
| **索引あり** | **4.93 ms**               | **7.18 ms** | **11,496** |
| 改善       | **80倍**                   | 82倍         | +20%       |


エラーはどちらも0件。

**注目すべき点が2つある。**

1. **索引ありの大データ(4.93ms)は、索引なしの中データ(15.41ms)よりも3倍速い。**
  データ量が5倍多いにもかかわらず、である。
   つまりこのアプリの性能を決めていたのはデータ量ではなく、索引の有無だった。
2. **スループットが20%増えた。** 待ち時間1秒のシナリオなのでリクエスト数は
  VU数でほぼ決まるはずだが、索引なしの場合は応答が遅くて
   1イテレーションが1秒に収まらず、実質的なスループットが落ちていた。

この結果により、8-1 で観測した「データ5倍で25.6倍の悪化」は
**データ量の問題ではなく索引の欠落による問題**であることが確定した。

## 9. 目標値と監視閾値の見直し



### 9-1. 計画時に置いた目標値は役に立たなかった

[パフォーマンステスト計画](perf-test-plan.md) の目標値は、実測値を知らない状態で
「ユーザーが待たされたと感じる境界」から逆算して置いた。結果は次の通りである。


| 対象                         | 目標(p95) | 中データ実測    | 余裕   | 大データ実測    | 余裕   |
| -------------------------- | ------- | --------- | ---- | --------- | ---- |
| `GET /posts?feed=all`      | 500 ms  | 15.41 ms  | 32倍  | 394.20 ms | 1.3倍 |
| `GET /posts/{id}/comments` | 500 ms  | 3.74 ms   | 134倍 | 3.22 ms   | 155倍 |
| `GET /users?q=`            | 800 ms  | 4.70 ms   | 170倍 | 5.13 ms   | 156倍 |
| `POST /auth/login`         | 1500 ms | 696.39 ms | 2.2倍 | —         | —    |


**中データでは全項目が桁違いに余裕があり、閾値としてまったく機能しなかった。**
一方、大データではフィード取得が目標の8割に迫っている。

つまりこの目標値は「今の実力を測る道具」としては粗すぎたが、
「限界に近づいたことを知らせる道具」としては大データでようやく意味を持ち始めた。

### 9-2. 実測に基づく目標値の提案

**平常時の実測値を基準に置き、そこから外れたことを検知できる水準にする。**


| 対象                         | 現行目標       | 提案                       | 根拠                                            |
| -------------------------- | ---------- | ------------------------ | --------------------------------------------- |
| `GET /posts?feed=all`      | p95 500ms  | **p95 50ms / p99 100ms** | 中データ実測 15.41ms の約3倍。索引を追加すれば大データでもこの水準に収まる見込み |

| `GET /users?q=`            | p95 800ms  | **p95 30ms**             | 実測 4.70ms の約6倍。将来の全件走査の悪化を早期に検知できる            |

これらは**改善を入れる前の現状値**に基づく。I-1(索引追加)を実施した後は、

### 9-3. 運用設計の監視閾値は飽和を検知できない

[運用設計](operations.md) の監視項目 #3 は「レイテンシ P99 が10分間3秒超で High」である。

**飽和テストで PostgreSQL の CPU が100%に張り付き、応答が平常時の78倍(p95 1.20s)に
劣化した状態でも、p99 は 1.58s でこの閾値を超えなかった。**

つまり現在の設定では、**サービスが完全に飽和してもアラートが上がらない。**


| 状態                     | 実測 p99     | 現行閾値(3s) |
| ---------------------- | ---------- | -------- |
| 平常時(中データ・VU50)         | 18.34 ms   | 超えない     |
| 大データ・VU50              | 587.03 ms  | 超えない     |
| **完全飽和(VU500・待ち時間なし)** | **1.58 s** | **超えない** |


3秒という値は、おそらく「ユーザーが明らかに異常だと感じる時間」から置いたものと思われる。
しかしこのアプリは飽和してもエラーを返さずキューイングで吸収するため(6-3参照)、
**3秒に達する頃には既に手遅れである。**

**提案:**


| #   | 項目               | 現行              | 提案                                          | 理由                                     |
| --- | ---------------- | --------------- | ------------------------------------------- | -------------------------------------- |
| M-1 | レイテンシ P99        | 10分間 3秒超 で High | **10分間 500ms超 で Warning / 10分間 2秒超 で High** | 平常時18msに対し500msは27倍。異常だが手遅れではない段階で気づける |
| M-2 | (新規)DBのCPU使用率    | —               | **5分間 80%超 で Warning**                      | 飽和の直接の原因。レイテンシより先に動く先行指標               |
| M-3 | (新規)コネクションプール使用率 | —               | **プール上限の80%超が5分継続で Warning**                | 飽和時に `db_active` がプール上限10に張り付いた        |


M-2 と M-3 は、レイテンシが悪化する**前**に動く先行指標である。
飽和テストでは、応答時間が目に見えて劣化する前に
PostgreSQL の CPU が上限に張り付き、`db_active` がプール上限に達していた。

ただし**メトリクスの収集基盤が現状は無い**([技術スタック](tech-stack.md) に
「メトリクスとトレースは未実装」と明記)。M-2 / M-3 を実現するには
`spring-boot-starter-actuator` + Micrometer の導入が前提になる。

### I-1 の具体案

```sql
-- V6__add_like_user_id_indexes.sql
CREATE INDEX idx_likes_user_id ON likes (user_id, post_id);
CREATE INDEX idx_comment_likes_user_id ON comment_likes (user_id, comment_id);
```

複合にして `post_id` / `comment_id` を含めるのは、`is_liked` の条件が
`user_id` と `post_id` の両方を使うため **Index Only Scan**(テーブル本体を読まない)に
なるからである。`user_id` 単独でも改善するが、索引からテーブルへの参照が1回増える。

### I-2 の具体案

```yaml
server:
  compression:
    enabled: true
    mime-types: application/json
    # 小さすぎるレスポンスは圧縮しても意味が無く、CPUを無駄に使う
    min-response-size: 1KB
```



### 実施しないことを推奨する項目

計測前に懸念として挙げたが、**実測の結果、現時点では手を入れる必要がないと判断したもの**:


| 項目                                               | 理由                                                                      |
| ------------------------------------------------ | ----------------------------------------------------------------------- |
| フィードの相関サブクエリ5本を JOIN + GROUP BY に書き換える           | 索引の効いている4本は 0.001ms/回。重いのは索引が無い1本だけで、それは I-1 で解決する。クエリ全体の書き換えはリスクに見合わない |
| `comment_count` の二重ネスト解消                         | 内側の EXISTS は `never executed`。短絡評価で到達していない                              |
| `posts(created_at)` / `posts(deleted_at)` への索引追加 | `ORDER BY p.id DESC` が主キー索引の逆順走査で足りている。書き込みコストだけ増える                     |
| `display_name` への索引追加(検索の高速化)                    | ユーザー数がこの規模では全件走査で十分速い。10章のスケーリング結果を見て判断する                               |




## 11. AWS構成を決める際の材料

本レポートの計測は、**AWS構成が未確定であるがゆえに実施した**とも言える。
[技術スタック](tech-stack.md) の「AWS移行の状況」にある通り、
ECS・RDS・ALB のいずれも未定義であり、S3 と IAM も現時点では destroy 済みである。

構成が決まってから測るのではなく、**測った結果を構成決定の入力にする**。
以下は、本レポートの実測から根拠を持って決められるようになった項目である。

### 11-1. ECSタスクのCPUとメモリの配分


| 観測                | 値                | 構成への含意               |
| ----------------- | ---------------- | -------------------- |
| 飽和時の backend CPU  | 48〜55%(上限2コア)    | **アプリ本体はCPUを使い切らない** |
| 飽和時の postgres CPU | 197〜203%(上限2コア)  | **律速はDB側**           |
| backend メモリ最大     | 373 MB(上限1024MB) | 1GBで十分に余裕がある         |
| postgres メモリ最大    | 106 MB(上限1536MB) | メモリは律速要因ではない         |


1. **CPUを厚くすべきはアプリではなくDBである。**
ECSタスクのCPUを増やしても、DBが同じままなら効果は薄い。
限られた予算をどちらに配分するかの判断材料になる。

ただし例外がある。**ログインはアプリ側のCPUを使う。**
BCrypt(cost 10)は p95 696ms を要し、これはDBではなくアプリのCPUで消費される。
ログインが集中する時間帯(朝など)がある場合は、アプリ側のCPUも必要になる。

### 11-2. RDSのインスタンスクラス

飽和は「2コアのPostgreSQLに対し50〜500VU」で発生した。
ただし**その飽和の主因は索引の欠落である**(8-3参照)。
索引を追加すれば1リクエストあたりのCPU消費が1/3以下になる。

**したがって RDS のクラス選定は I-1(索引追加)を実施してから行うべきである。**
索引が無い状態を前提にクラスを選ぶと、必要以上に大きなインスタンスを
選んでしまい、月額費用を無駄に払い続けることになる。

### 11-3. HikariCP のプールサイズと RDS の `max_connections`


| 観測                   | 値                                         |
| -------------------- | ----------------------------------------- |
| 現在のプールサイズ            | 10(Spring Boot既定。`application.yml` に指定なし) |
| アイドル時の接続数            | 10(`minimumIdle` も既定10のため、待機中も保持し続ける)     |
| 負荷テスト(VU50)時の同時アクティブ | 最大 6〜7                                    |
| 飽和時の同時アクティブ          | **10(上限に張り付く)**                           |


設計上の制約は次の式で決まる。

```
ECSタスク数 × HikariCPプールサイズ ≦ RDS の max_connections
```

**現状はプールサイズが明示されていないため、この式を検証できない。**
タスク数を増やしたときに RDS の接続上限を超える事故が起きうる。
I-6(プールサイズの明示)を先に実施し、その値を前提にタスク数の上限を決める必要がある。

なお `minimumIdle` が既定で `maximumPoolSize` と同じであるため、
**アイドル時も常時10接続を保持する。** タスクを10個並べれば、
無負荷でも100接続をRDSに対して張り続けることになる。

### 11-4. ALB / ターゲットグループのタイムアウト

**このアプリは過負荷時にエラーを返さず、キューイングで吸収する**(6-3参照)。
飽和時の実測は p95 1.20s / max 2.91s だった。

ALB の idle timeout(既定60秒)や、ターゲットグループのヘルスチェック間隔を
決めるには、**アプリ側が何秒でエラーを返すかを先に決める必要がある。**
現状は HikariCP の `connection-timeout` 既定30秒がその役割を担っているが、
明示されていない(I-6)。

**アプリのタイムアウト < ALBのタイムアウト** の関係を保たないと、
ALB が先に切ってしまい、アプリ側にはエラーログが残らない。

### 11-5. CloudFront導入の優先度


| 観測                 | 値                               |
| ------------------ | ------------------------------- |
| フロントのバンドル          | 310.57 KB(gzip 93.21 KB)、単一チャンク |
| Fast 4G でのバンドル取得時間 | 271〜300 ms                      |
| APIレスポンスの圧縮        | **無効**                          |
| 計測対象ページの画像         | **0枚(検証できず)**                   |


静的アセット(JS/CSS)については、CDN より先に
**I-2(レスポンス圧縮)と I-7(コード分割)の方が効果が大きい。**
圧縮だけで転送量は 1/3 になる。

画像については**今回検証できていない**(7-6参照)ため、
CloudFront + サムネイル生成の要否は判断できない。
画像を含むデータで測り直す必要がある。

### 11-6. オートスケールのトリガ指標

**CPU使用率をトリガにする場合、どのCPUを見るかで結果が変わる。**

飽和時、backend のCPUは48〜55%にとどまっていた。
つまり**アプリのCPU使用率を見てスケールアウトを判断すると、
DBが飽和していてもスケールしない。** タスクを増やしてもDBの負荷が増えるだけで、
状況は悪化する。


| 指標             | 適否                          |
| -------------- | --------------------------- |
| ECSタスクのCPU使用率  | **単独では不適**。飽和時も50%程度にしかならない |
| RDS の CPU使用率   | **適切**。飽和の直接の原因             |
| ALB のターゲット応答時間 | 適切だが遅行指標                    |
| ALB のリクエスト数    | 補助的に有効                      |




### 11-7. AWS構成が固まった時点でやること

本レポートの計測資産は、そのまま本番構成に対して再実行できる。

```powershell
$env:BASE_URL = "https://api.example.com/api"
$env:PERF_PROFILE = "load"
k6 run perf/k6/scenarios/timeline.ts
```

`perf/k6/lib/config.ts` が接続先を環境変数から読むようにしてあるため、
**シナリオの変更は不要**である。本レポートの数値と突き合わせることで、
「ローカルとの差がどこから来ているか」を切り分けられる。

## 12. この測定の限界

### 12-1. 環境に由来する限界

### 12-3. 測定手順そのものに起因する注意点


| 注意点                          | 内容                                                                                                                 |

| **計測中にデータが増える**              | `write` / `mixed` シナリオが投稿を作る。負荷フェーズ中に posts が 20,000 → 24,457 に増えた。後半のフェーズほど多いデータで測られている                           |

### 実装時に判断した点

**I-6 で `connection-timeout` を既定の30秒から10秒に短縮した。**
30秒のままだと上流(ALB の idle timeout は既定60秒)との関係が曖昧になり、
上流が先に切った場合に**アプリ側にエラーが残らないまま利用者だけがエラーを見る**状態になる。
アプリのタイムアウトが上流より短ければ、アプリのログに必ず記録が残る。

**I-6 で `minimum-idle` を 2 にした。**
HikariCP の既定では `minimum-idle` は `maximum-pool-size` と同じ値になり、
無負荷でも上限数の接続を保持し続ける。タスクを10個並べれば、
誰も使っていなくても100接続を RDS に張ることになる(11-3参照)。

**I-8 の根拠。**
このクエリが聞いているのは「いま読み込んだ最新の投稿より新しい投稿はあるか」である。
読み込んだ直後に同じことを聞けば、答えは定義上「無い」。
つまりマウント時の取得は確実に空を返す、純粋な無駄だった。
`initialData` で「データを持っている」状態から始め、`refetchOnMount: false` で
マウント時の再取得を止めた。ウィンドウにフォーカスが戻ったときの確認は残している。

### 計測スクリプトを TypeScript に統一した

フロントエンドが TypeScript であるのに対し、計測スクリプトは JavaScript で書いていた。
リポジトリ内で言語が混在していたため、`perf/` 配下のスクリプトを TypeScript へ移行した。

**移行にあたって確認した重要な事実: k6 も Node も、TypeScript の型検査をしない。**
どちらも型を「剥がす」だけである。実際に次のファイルを渡したところ、
エラーも警告も無く最後まで実行された。

```typescript
const wrong: number = "this is not a number";   // 明らかな型エラー
```

つまり**拡張子を `.ts` に変えるだけでは、型があるつもりで実は無い状態**になり、
かえって誤解を招く。そこで型検査を別に回す仕組みを用意した。

| 対応 | 内容 |
|---|---|
| 型定義 | `@types/k6` 2.2.0 を `frontend/devDependencies` に追加(k6本体と同バージョン) |
| 設定 | `perf/tsconfig.json`。`typeRoots` で `frontend/node_modules/@types` を参照 |
| 実行 | `cd frontend && npm run typecheck:perf`(`tsc --noEmit`) |
| CI | frontend ジョブに「Type check performance test scripts」を追加 |

型検査が実際に機能することは、意図的な型エラーを注入して `error TS2322` が
出ることと、戻すとクリーンになることの両方で確認した。
移行の過程で未使用の import が1件検出されている。
