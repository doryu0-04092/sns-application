# 振り返り — AWSデプロイで分かったこと

設計からデプロイ、動作確認、破棄までを一通り行った(2026-08-28、PR #65〜#85)。その過程で分かったことを記録する。

**この文書の目的は、次に同じことをするときに同じ失敗を繰り返さないことである。** うまくいったことより、**想定と違ったこと**を厚く書いた。

---

## 1. デプロイして初めて分かったこと

設計とローカルのテストがすべて通っていても、実際にAWSへ適用するまで分からないことがあった。以下はすべて「apply して初めて表面化した」ものである。

### 1-1. `terraform validate` もCIも、APIの値制約は検出できない

セキュリティグループの説明を日本語で書いていたところ、apply が失敗した。

```
InvalidParameterValue: Value (ALB: CloudFrontのエッジからのHTTPのみ受け付ける)
for parameter GroupDescription is invalid. Character sets beyond ASCII are not supported.
```

**EC2 APIはセキュリティグループの説明に非ASCIIを受け付けない。** セキュリティグループ本体だけでなく、ingress/egressルールの説明にも同じ制約がかかる。

重要なのは、`terraform validate` もCIのterraformジョブも**これを検出できない**という点である。どちらもHCLの構文と参照の整合性しか見ない。値がAWSに受け入れられるかは、実際にリクエストを投げるまで分からない。

同じ日本語の説明でも、CloudFrontのOAC・SSMパラメータ・ECRのライフサイクルポリシーは**すべて作成に成功している**。制約はEC2 APIに固有だった。

**教訓**: リソースの属性になる文字列(`name` / `description` / `comment`)は「コードベースの外に出て検証されるもの」として扱う。Terraform内部で完結する `variable` や `output` の `description` とは性質が違う。識別子と説明は既定でASCIIにし、日本語はコメント側に置けば情報は失われない。

### 1-2. サービスプリンシパルにはバケットポリシーが要る

画像が `/images/posts/<key>.png` で403になった。原因は**画像バケットにCloudFront用のバケットポリシーを付け忘れていた**こと。

コードにはこう書いていた。

> バケットポリシーは置かない。同一アカウント内であればIAM側の許可だけで到達でき、許可の置き場所を1箇所に保てるため。

これが成り立つのは**IAMプリンシパル**(ECSタスクロール)の場合だけだった。CloudFrontのOACは**サービスプリンシパル**でIAMロールを持たないため、バケットポリシーでの明示的な許可が要る。

同じバケットに性質の異なる2つのアクセス経路があり、許可の与え方が別だという点を見落としていた。静的サイト用バケットには正しく書けていたので、**片方だけ書けている状態**が一番気づきにくい。

### 1-3. `docker build` の既定がECSで動かないイメージを作る

buildxは既定でprovenanceとSBOMのattestationを付ける。その結果pushされるのは**OCIイメージインデックス**になり、amd64のイメージとattestationマニフェストが同居する。

```
sha256:fcf2180…  tags: [latest]  OCIイメージインデックス
sha256:b0476bd…  tags: なし      amd64のイメージ本体
sha256:46d8c81…  tags: なし      attestationマニフェスト(1,895バイト)
```

ECS Fargateはこの形式を取得できないことがある。`--provenance=false --sbom=false` を付けると `latest` が素の `application/vnd.docker.distribution.manifest.v2+json` を指すようになる。

**push直後にECRのマニフェスト種別を確認しておくと、15分待ってから失敗するのを避けられる。**

### 1-4. 適用の順序に依存関係がある

`terraform apply` を一度に流すと、ECRにイメージが無い状態でECSサービスがタスクを起動しようとして失敗する。`deployment_circuit_breaker` が作動して apply 全体が止まる。

順序を分ける必要がある。ECRを作る → イメージをpush → 残りをapply。

**結果的にこの分割は別の役目も果たした。** ECRだけを先に作る段階(ほぼ無料)で問題があれば、ALBとRDSという課金の始まるリソースを作る前に気づける。実際、セキュリティグループの失敗はALBより手前で止まり、課金が発生する前に修正できた。

### 1-5. 未検証だった設計上の懸念が解消した

設計時点で「`/images/*` の署名付きCookieの検証が、URIを書き換えるCloudFront Functionより先に走るか」を確認できておらず、順序が逆なら失敗する懸念を残していた。代替案も用意していた。

**検証が先に走ることを確認できた。** 根拠は、Cookieを持つリクエストが `MissingKey`(CloudFrontの署名検証エラー)ではなく `AccessDenied`(S3のエラー)を返したこと。署名検証を通過してS3まで到達していた。代替案は不要になった。

## 2. 環境固有の罠(Windows)

### 2-1. Git Bashが先頭スラッシュをWindowsパスに変換する

これが**最も危なかった**。

```bash
VITE_API_BASE_URL=/api npm run build
```

これで作った成果物に焼き込まれた値は、

```js
Mi=`C:/Program Files/Git/api`
```

**Git Bash(MSYS)が `/api` をWindowsパスに変換していた。** そのまま配置していれば、全API呼び出しが `C:/Program Files/Git/api/auth/login` に飛ぶサイトが公開されていた。ビルドは成功し、型検査もlintも通る。

同じ変換をCloudWatchのロググループ名(`/ecs/...`)でも踏んだ。

**回避策**: `MSYS_NO_PATHCONV=1` を付けるか、PowerShellで実行する(`$env:VITE_API_BASE_URL = "/api"`)。

### 2-2. PowerShellでは `-target=` に引用符が要る

```powershell
terraform apply -target=aws_ecr_repository.backend
# Error: Invalid target "aws_ecr_repository"
```

引数が分解されて `.backend` が落ちる。`terraform apply "-target=aws_ecr_repository.backend"` と囲む必要がある。

**手順書はPowerShell向けに書いていたのに、この形になっていなかった。** 手順書は実際に実行するまで検証されていない、ということでもある。

## 3. テストについて分かったこと

### 3-1. テストが不具合を内包していた

デプロイ先で、別のユーザーでログインすると**前のユーザーのいいね・フォロー状態が表示される**不具合が見つかった。ログアウト時に `meKeys`(ログイン中ユーザー)しか無効化しておらず、投稿一覧のキャッシュに含まれる `isLiked` / `isFollowing` が残っていた。

既存のテストはこう書かれていた。

```ts
expect(invalidateQueries).toHaveBeenCalledWith({ queryKey: meKeys.all });
```

**呼び出しを検証する形だったため、テストと実装が「meだけ消せばよい」という同じ思い込みを共有していた。** 単体テスト199件・E2E18件がすべて緑でも検出できない。

修正では、テストを「呼び出しの検証」から「**キャッシュの中身が実際に消えることの検証**」に変えた。

**教訓**: 何を呼んだかではなく、何が起きたかを検証する。呼び出しの検証は、実装の意図をそのまま写しただけになりやすい。

### 3-2. 失敗するテストが毎回入れ替わるのはタイミング依存の兆候

E2Eで2件失敗したので再実行したところ、その2件は成功し、**別の1件が失敗**した。3件の失敗のうち2件は同じアサーションだった。

特定のテストが再現的に落ちるのではなく落ちる場所が動くのは、機能不全ではなくタイミング依存を示す。原因は `expectRecovered` が待つ処理が「401 → リフレッシュ → 再試行 → 再描画」の**逐次3往復**で通常2秒かかるのに対し、`expect` のタイムアウトが既定の5秒しかなく、`playwright.config.ts` が `retries: 0` だったこと。

対処として待ち時間を15秒にした。**アサーションの内容は変えていないので検出力は落ちない**(回復が壊れていればログイン画面へ送られ、何秒待っても表示名は出ない)。失うのは失敗に気づくまでの時間だけ。

`retries` を増やす案は採らなかった。失敗を握りつぶす方向になるため。

### 3-3. テストの失敗と環境の問題を区別する

Docker Desktopが起動していない状態でバックエンドのテストを回すと、497件中116件が「エラー」になった。すべて `Could not find a valid Docker environment` で、テストロジックの失敗ではない。

数字だけ見れば「116件失敗」だが、意味はまったく違う。**失敗の件数ではなく、失敗の中身を見る必要がある。**

## 4. 検証手順そのものについて

### 4-1. 成果物を実際に見る手順が、壊れたリリースを1回止めた

「ビルドが成功した」は「正しい値が焼き込まれた」を意味しない。配置の前に成果物をgrepする手順を入れていたおかげで、2-1の壊れたビルドを配置前に止められた。

```bash
grep -o '.\{20\}/api.\{20\}' dist/assets/index-*.js   # 実際の焼き込み値
grep -c "localhost:8080" dist/assets/*.js             # 誤った値が無いこと
```

**間違った設定ほど、静かに成功したように見える。**

### 4-2. エラーの切り分けはレスポンスの差から

画像の403を調べたとき、Cookieの有無でレスポンスが変わることが決め手になった。

| | エラーコード | server |
|---|---|---|
| Cookie無し(curl) | `MissingKey` | CloudFront |
| Cookie有り(ブラウザ) | `AccessDenied` | **AmazonS3** |

**どの層が拒否しているかが、エラーの中身から読み取れた。** 「403だから権限の問題」で止めず、誰が返した403かを見ることで原因の層が特定できた。同時に、懸念していた署名検証の順序も問題ないと分かった(1-5)。

### 4-3. ローカルのテストが全部緑でも、デプロイ先の確認で不具合が出る

3-1のキャッシュ残留は、ローカルの単体テスト・E2Eをすべて通過していた。実際にブラウザで2ユーザーを切り替えて初めて見つかった。

**環境の違いではなく、テストの観点の欠落が原因だった**点が重要である。ローカルでも同じ操作をすれば再現したはずで、「デプロイしないと分からなかった」わけではない。

## 5. 進め方について

### 5-1. 許可を事前に分類しておくと流れが切れない

長い作業の前に、打つコマンドを洗い出して分類した。

- **一括で許可してよいもの**: 可逆・高頻度。読み取り系CLI、ビルド、テスト、`terraform plan`、`docker compose`
- **都度確認するもの**: `terraform apply` / `destroy`(課金が始まる)、`gh pr merge`(不可逆)、外部への書き込み、依存の追加

`terraform plan` を**あえて一括許可側に置いた**。都度確認にすると、差分を見ずに apply する動線ができてしまう。planは状態を変えない。

ワイルドカードは前方一致なので `Bash(gh pr *)` は `gh pr merge` まで通ってしまう。**動詞まで指定して列挙する**必要がある。

### 5-2. 手順書は実行するまで検証されていない

自分で書いた `infra/README.md` の手順が、2箇所そのままでは動かなかった(2-1、2-2)。どちらも実際に実行して初めて分かった。

**手順書を書いた時点では「書いた」だけで、「動く」ことは確認できていない。**

## 6. うまくいった設計判断

失敗ばかりではないので、実測で裏が取れたものも記録しておく。

- **単一ドメイン方式** — フロント・API・画像をすべてCloudFrontから配信したことで、CORSとクロスサイトCookieの問題が構造的に消えた。分離方式なら `SameSite=None; Secure` への変更とALB用の証明書が必要だった
- **`/api/*` のキャッシュ無効** — 実測で毎回 `x-cache: Miss`。Cookie認証で内容が閲覧者ごとに違うAPIをキャッシュする事故を防げた
- **画像の署名付きCookie** — URLが固定になり、2回目以降 `Hit from cloudfront`(`Age: 1`)。同時にURL自体が秘密でなくなり、コピー・Referer・ログ経由の漏洩経路が塞がった
- **ALBの二重の絞り込み** — プレフィックスリスト＋シークレットヘッダー。**403に到達する前に接続タイムアウトした**。想定より強く、ネットワーク層で止まっていた
- **段階的なapply** — 課金の始まるリソースの手前で失敗を検出できた(1-4)

## 8. 費用について

学習用の最小構成でも、ALBとRDSが起動しているだけで**月$40〜50**かかる。使い終わったら `terraform destroy` する運用を前提にした。

destroyしてもTerraformのコードは残るので作り直せる。ただし**S3バケットに中身が残っているとdestroyが失敗する**ため、先に空にする必要がある。手順は [infra/README.md](../infra/README.md) にある。
