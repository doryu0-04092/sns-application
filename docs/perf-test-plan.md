# パフォーマンステスト計画

[テスト計画](test-plan.md) が扱う L1〜F2 の7層は、すべて「正しく動くか」を検証するものである。本書はそれとは別に、**「どれだけ速いか」「どこで壊れるか」** を検証する計画を定める。

## 0. この計画で測るもの・測らないもの

「パフォーマンステスト」は複数の意味を含む語なので、先に線引きする。

| 種別 | 内容 | 本計画 |
|---|---|---|
| 負荷テスト(load) | 想定内の負荷での応答性を測る | 実施する |
| ストレステスト(stress) | 負荷を上げ続けて限界点と壊れ方を探す | 実施する |
| 耐久テスト(soak) | 一定負荷をかけ続けて劣化を見る | 実施する(30分) |
| スパイクテスト(spike) | 瞬間的な急増への追従と回復を見る | 実施する |
| フロントエンド計測 | 初回読み込みと操作継続時の描画性能 | 実施する |

**実施場所はローカル(Docker Desktop on Windows)である。** AWS構成が未確定であるため([技術スタック](tech-stack.md) の「AWS移行の状況」を参照)、本番環境での計測は現時点で実行できない。

この制約から、本計画が追うのは主に次の2つである。

- **相対比較** — エンドポイント間の差、データ量が増えたときの劣化率
- **壊れ方の質** — 何が先に枯渇するか、エラーを返すか無限に待つか、回復するか

**応答時間の絶対値は本番の性能保証にならない。** 測定側(k6)と被測定側(Docker)が同一PC上で動くため、絶対値はこの1台の性能に依存する。

## 1. なぜ先に目標値を決めるのか

[要件定義](requirements.md) の非機能要件には性能に関する記述が無い。目標値を決めずに測ると、数字が出ても良し悪しを判断できず、結果を見てから基準を後付けすることになる。それでは「遅い」と言えなくなるため、測る前に決める。

なお [運用設計](operations.md) の監視項目には「レイテンシ P99 が10分間3秒超で High」という閾値が既に存在するが、これは実測に基づかない値である。本計画の実測結果をもって、この閾値の妥当性も併せて見直す。

## 2. 負荷テストの目標値

ローカルDocker環境でのベースラインとして仮置きする値であり、実運用のSLOではない。実測後にレポートで見直す。

| # | 対象 | 指標 | 目標 | この値にした理由 |
|---|---|---|---|---|
| P-1 | `GET /api/posts?feed=all&limit=20` | p95 / p99 | 500ms / 1000ms | 最も高頻度で叩かれる画面(タイムライン)。ユーザーが「待たされた」と感じ始める境界を500msに置く |
| P-2 | `GET /api/posts?feed=following` | p95 / p99 | 500ms / 1000ms | P-1 と同じ画面のタブ切り替えなので同一基準 |
| P-3 | `GET /api/posts/{id}/comments` | p95 | 500ms | 投稿詳細を開いた直後に走る。ページングが無く全件返すため、悪化するなら真っ先にここ |
| P-4 | `GET /api/users?q=` | p95 | 800ms | 検索は多少待たされても許容されるため P-1 より緩める |
| P-5 | `POST /api/auth/login` | p95 | 1500ms | BCrypt(cost 10)が数十〜数百ms を必ず消費する。他と同じ基準では意味が無いので別枠にする |
| P-6 | `POST /api/posts` | p95 | 800ms | 書き込み。画像なしの投稿のみを対象とする |
| P-7 | 全エンドポイント | エラー率 | < 1% | 想定内の負荷でエラーが出ること自体が不合格 |

## 3. ストレス・耐久・スパイクの合格条件

これらは数値の閾値では合否を決められない。壊すことが目的だからである。そのため**挙動で合格条件を定義する**。

| # | 種別 | 合格条件 | 不合格とみなすもの |
|---|---|---|---|
| B-1 | ストレス | 飽和したらエラーを返し、負荷を戻せば性能も戻る | ハングする / 無限に待つ / プロセスが死ぬ / 負荷を戻しても回復しない |
| B-2 | 耐久 | 30分間、メモリ・DBコネクション数・応答時間が単調増加しない | いずれかが右肩上がり(リークの疑い) |
| B-3 | スパイク | 負荷を戻してから60秒以内に平常値へ戻る | 60秒を超えても戻らない / 急増後に回復しない |

B-1 で「エラーを返すこと」を合格としているのは、**過負荷時に速やかに失敗を返すほうが、待たせ続けるより回復が速いため**である。無限に待つ実装は、上流(ALB等)のタイムアウトと二重に待ち時間が積み上がる。

## 4. フロントエンドの目標値

| # | 指標 | 目標 | 測り方 |
|---|---|---|---|
| F-1 | Lighthouse Performance スコア | >= 80 | 本番ビルド(`npm run build` + `npm run preview`)に対して監査 |
| F-2 | LCP (最大コンテンツの描画) | < 2.5s | 同上 |
| F-3 | CLS (レイアウトのずれ) | < 0.1 | 同上 |
| F-4 | TBT (操作を受け付けない合計時間) | < 200ms | 同上 |
| F-5 | スクロール継続時の描画時間 | 増加が線形以下 | パフォーマンストレースで5ページ分スクロールし推移を見る |

**開発サーバ(`npm run dev`)では測らない。** 未minifyかつHMR込みで、本番と別物の数字になるため。

## 5. 測定環境

| 項目 | 値 |
|---|---|
| 計測用スタック | `docker-compose.perf.yml`(Composeプロジェクト名 `snsapp-perf`) |
| ポート | backend 18080 / postgres 55432 / localstack 54566 |
| DB | `sns_application_perf`(開発用 `sns_application` とは別) |
| backend のリソース上限 | CPU 2コア / メモリ 1024MB |
| postgres のリソース上限 | CPU 2コア / メモリ 1536MB |
| 負荷ツール | k6 v2.2.0 |

backend を2コアに絞っているのは、**飽和点を k6 側ではなくアプリ側に現れさせるため**である。ホストは20コアあるため、アプリを絞らないと k6 が先に頭打ちになり「何が飽和したのか」が分からなくなる。

## 6. データ量

段階式にする。小データでスクリプトの不具合を潰してから中データで本番計測に入ることで、結果が悪かったときに「スクリプトのバグか、アプリの限界か」を切り分けられる。

| | users | posts | comments | likes | follows |
|---|---|---|---|---|---|
| 小(手順確立用) | 50 | 1,000 | 3,000 | 5,000 | 500 |
| 中(本番計測) | 500 | 20,000 | 60,000 | 100,000 | 10,000 |

投入は `perf/seed/seed.sql` によるSQL直接実行とする。API経由で2万件を作ると投入だけで十数分かかり、かつ投入行為そのものが負荷テストになってしまうため。

ただしSQL直接投入はアプリの不変条件を迂回するため、`perf/seed/verify.sql` で以下を確認してから計測に入る。

- `likes` / `comment_likes` / `follows` の UNIQUE 制約違反が無い
- `comments.parent_comment_id` が同じ `post_id` のコメントを指している
- 自分自身をフォローしている行が無い

投入後は `ANALYZE` を必ず実行する。統計情報が無いとプランナが誤った実行計画を選び、測定結果が実態とずれるため。

## 7. シナリオ

| ファイル | 再現する操作 | 狙って踏むコード |
|---|---|---|
| `timeline.js` | フィード1ページ目 → cursorで2ページ目 → いいね | `PostMapper.findFeedAll`(相関サブクエリ5本) |
| `following-feed.js` | `feed=following` でフィード取得 | `PostMapper.findFeedFollowing`(JOINが1本増える) |
| `post-detail.js` | 投稿詳細 → コメント一覧 | `CommentMapper.findByPostId`(LIMITなし全件) |
| `search.js` | ユーザー検索 | `UserMapper.search`(索引なし列への両端ワイルドカード) |
| `write.js` | 投稿作成(画像なし) | `PostMapper.insert` |
| `login.js` | ログインのみ | BCrypt検証を独立して測る |
| `mixed.js` | 上記を実利用比率で混合 | ストレス・耐久・スパイクで使う |

### シナリオ共通の設計判断

**ログインはVUごとに1回だけ行う。** BCrypt(cost 10)は1回あたり数十〜数百msのCPUを消費するため、毎イテレーションでログインすると測定値がBCryptに支配され、本来測りたいクエリ性能が数字に現れない。k6 の cookie jar は VU の生存期間を通じて維持されるため、初回だけ実行すれば足りる。ログイン自体の性能は `login.js` で独立して測る。

**VUごとに別ユーザーを使う。** 全VUが同一ユーザーだと `is_mine` / `is_following` / `is_liked` の計算結果がキャッシュに乗り続け、実際より速い数字が出る。

**すべてのレスポンスでステータスコードを検証する。** 認証に失敗した場合、`JwtAuthFilter` はDBに触れず即座に401を返すため**異常に速い数字が出る**。検証が無いと、この誤りに気づかないまま「性能が良い」と結論づけてしまう。

**耐久テストではリフレッシュ経路を通す。** アクセストークンの寿命は15分なので、30分の耐久テスト中に必ず失効する。`POST /api/auth/refresh` を組み込むことで測定が途中で無意味にならず、同時にリフレッシュトークンのローテーション処理を長時間動かす検証にもなる。

## 8. 負荷プロファイル

| ファイル | 種別 | ステージ |
|---|---|---|
| `load.js` | 負荷 | 30s→10VU, 2m→50VU, 30s→0 |
| `stress.js` | ストレス | 50→100→150→200→250→300VU(各1分)、その後50VUに戻して2分観測 |
| `soak.js` | 耐久 | 2m→20VU, 26m→20VU維持, 2m→0(計30分) |
| `spike.js` | スパイク | 30s→10VU, 10s→200VU, 1m→200VU, 10s→10VU, 2m→10VU(回復観測) |

ストレスには**自動中断ガード**を入れる(エラー率20%超 または p95 が10秒超で停止)。無制限に上げ続けるとホストごと巻き込むため。

## 9. リソースの観測

応答時間だけでは「何が枯渇したか」が分からない。`perf/monitor/collect.ps1` が5秒間隔で以下をCSVに記録する。

| 観測対象 | 取得方法 | 何が分かるか |
|---|---|---|
| コンテナのCPU / メモリ | `docker stats` | メモリの右肩上がり = リークの疑い |
| DBコネクション数 | `pg_stat_activity` の件数 | HikariCP既定10本で頭打ちになるかが直接見える |
| DBの待機イベント | `pg_stat_activity.wait_event_type` | ロック待ちかI/O待ちかCPU待ちか |
| 遅いクエリ | `pg_stat_statements` | どのSQLが総実行時間を食っているか |

**コネクションプールの枯渇は外から判別できる。** HikariCP の `connection-timeout` 既定値は30秒なので、枯渇すると「30秒待ってから例外」になる。`pg_stat_activity` が10で張り付き、かつ p99 が30秒に張り付いていれば、原因はプールサイズだと特定できる。

JVMヒープの内訳・GC回数・プールの待機キュー長を精密に見るには `spring-boot-starter-actuator` + Micrometer の追加が必要だが([技術スタック](tech-stack.md) に「メトリクス未実装」と明記)、**本計画ではアプリを変更しない**。まず無改変で測り、`docker stats` のメモリが右肩上がりだった場合に限り、原因特定の手段としてレポートで追加を提案する。

## 10. クリーンアップ

計測用スタックは Composeプロジェクト名・ポート・ボリューム・DB名のすべてが開発用と別である。したがって次のコマンドで破棄しても、開発用の `sns-application_pgdata` には一切触れない。

```
docker compose -p snsapp-perf -f docker-compose.perf.yml down -v
```

`-v` でボリュームごと消えるため、「削除SQLの書き漏れ」が原理的に起きない。**テストが失敗した場合・中断した場合も必ず実行する。** 特にストレステストは意図的に壊すため、途中で止まる前提で手順を組む必要がある。

破棄後の確認:

1. `docker volume ls` に `snsapp-perf` 関連のボリュームが1件も無い
2. `docker ps -a` に perf コンテナが無い
3. 開発用ボリューム `sns-application_pgdata` が計測前と同じく存在する

## 11. 本計画で行わないこと

| 項目 | 理由 |
|---|---|
| AWS環境での計測 | 本計画の策定時点では構成が未確定で、測る対象が存在しなかった。**その後2026-08-28にデプロイしたが、機能確認を終えた時点でdestroyしたためAWS環境での計測は行っていない**(→[AWS構成設計](aws-architecture.md))。再構築して計測する場合は `perf/README.md` の手順で `BASE_URL` を差し替える |
| 改善の実装 | 計測と改善を同時に行うと、効果測定の土台が無い状態で改善を入れることになる。本計画は改善案の提示までとする |
| アプリ本体のコード変更 | 上に同じ。Actuator の追加も提案に留める |
| 画像アップロードの負荷 | S3へのPUTはバックエンドを経由しないため、アプリの性能とは別の話になる |
| ブラウザを多数同時起動しての実測 | k6 browser モジュールが必要。フロントは単一セッションでの計測に留める |
