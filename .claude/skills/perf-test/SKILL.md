# perf-test: 計測用スタックの起動〜レポート作成〜クリーンアップ

計画と合格条件は [docs/perf-test-plan.md](../../../docs/perf-test-plan.md)、実行手順の詳細は [perf/README.md](../../../perf/README.md) にある。**このskillを使う前に、その2つを読むこと。**

## 発動条件

- `/perf-test` と明示入力された場合: 確認なしでそのまま手順を開始する。
- 会話内で発動する場合: 「パフォーマンステストを実施して」のようにワークフロー全体の実行を明確に指示された場合に限り、実行前に一度確認してから進める。
- 「遅い気がする」「速くしたい」のような曖昧な相談では発動しない(通常の会話として応答する)。

## 手順

1. **範囲の確認**: 停止点として `AskUserQuestion` で以下を確認する。地の文で質問して返信を待つ形式は使わない。
   - 計測対象: ローカル(既定) / AWS(`BASE_URL` を差し替える)
   - データ量: 小(手順確認) / 中(本番計測)
   - 実施するテスト種別: 負荷 / ストレス / 耐久 / スパイク / フロントエンド(複数選択)
   - **PCの占有時間を明示する**: ストレス約10分、耐久30分。この2つは他の作業と並行できない。

2. **前提の確認**: `k6 version` と `docker version` が通ることを確認する。k6 が無ければ `winget install GrafanaLabs.k6`(依存の追加なので許可を得る)。

3. **計測用スタックの起動**: `docker compose -p snsapp-perf -f docker-compose.perf.yml up -d --build`。
   - `curl http://localhost:18080/api/health` が 200 を返すまで待つ。
   - `docker inspect snsapp-perf-backend-1 --format '{{.HostConfig.NanoCpus}}'` でリソース制限が実際に効いていることを確認する。効いていないと測定値がホストの空き状況で毎回変わる。
   - `CREATE EXTENSION IF NOT EXISTS pg_stat_statements;` を実行する。

4. **シード投入と検証**: `perf/seed/seed.sql` → `perf/seed/verify.sql`。
   - **「不変条件の検証」が全て 0 であることを確認してから次へ進む。** SQL直接投入はアプリの不変条件を迂回するため、壊れたデータのまま計測すると遅さの原因がアプリなのかデータなのか分からなくなる。
   - 「コメント数が多い投稿 上位5件」に出たIDを控え、以降 `PERF_HOT_POST_IDS` に渡す。
   - **投入直後にベースラインの行数を記録する。** `write` シナリオが計測中に投稿を作るため、後半のフェーズほどデータ量が多い状態で測られる。

5. **スクリプトの動作確認(飛ばさない)**: 本番計測の前に必ず全シナリオをスモークで通す。
   - `PERF_PROFILE=smoke` で7シナリオ
   - **ストレス・スパイクを実施するなら `PERF_PROFILE=smoke-preauth` も必ず通す。** 通常の smoke は preAuth=false なので、setup で50人分ログインして cookie jar に配る経路が一度も実行されない。未検証のまま本番に入ると、9分かけて全リクエストが401になる事故が起こりうる。
   - 確率的な不備を拾うため2〜3周させる。1周だと分岐に入らず見逃す。

6. **観測スクリプトの起動**: `perf/monitor/collect.ps1` を別プロセスで回す。**ストレス・耐久・スパイクでは必須。** 応答時間だけでは何が枯渇したか分からない。

7. **計測の実行**: `PERF_PROFILE` を切り替えて `k6 run --summary-export perf/results/<種別>-<シナリオ>.json`。軽い順(負荷→スパイク→ストレス→耐久)に実行する。

8. **フロントエンド計測**: `npm run build`(サイズ記録) → `npm run preview` → Lighthouse監査とパフォーマンストレース。
   - **`new_page` には必ず `isolatedContext` を指定する。** 指定しないと本人のブラウザのタブに混ざる。
   - **開発サーバ(`npm run dev`)では測らない。** 未minify・HMR込みで本番と別物の数字になる。
   - モバイル条件は `emulate` を使う。`resize_page` は最小500pxまでしか下げられないため、`evaluate_script` で `window.innerWidth` を確認して実際に適用されたことを検証する。

9. **レポート作成**: `docs/perf-test-report.md` を更新する。既存の `docs/test-plan.md` / `docs/operations.md` に合わせ、表主体＋その下に「なぜそうしたか」を散文で添える。
   - **全ての数値に `perf/results/` の裏付けを対応させる。**
   - **測定の限界を必ず書く。** ローカル実施なので絶対値は本番の性能保証にならない。「VU300まで耐えた」を「本番でも300同時接続に耐える」と読まれると誤りになる。
   - AWS構成が未確定なら、「この測定から根拠を持って決められるパラメータ」を書く。

10. **クリーンアップ(必須)**: `docker compose -p snsapp-perf -f docker-compose.perf.yml down -v`。
    - **計測が失敗・中断した場合も必ず実行する。** ストレステストは意図的に壊すため、途中で止まる前提で手順を組んでいる。
    - 確認: `docker volume ls` に `snsapp-perf` 関連が0件、開発用 `sns-application_pgdata` が残っていること。

11. **PRとCI**: `/open-pr` でPRを作り、**CIが緑であることを確認してから**完了報告する。マージは別途確認を取る。

## 踏みやすい罠(すべて実際に踏んだもの)

| 罠 | 症状 | 対処 |
|---|---|---|
| k6 がイテレーションごとに cookie jar をリセットする | 各VUの2回目以降が全て401。**401は認証フィルタがDBに触れず即返すので応答が異常に速く、「高性能」という誤った結果が出る** | `noCookiesReset: true`。併せて全レスポンスでステータスを検証する |
| シードSQLの整数オーバーフロー | 小データでは通るが中データで `integer out of range` | `g.n::bigint * 素数` とキャストする |
| PowerShell 5.1 が BOM 無し UTF-8 を読めない | 日本語コメントが化け、構文エラーになる | `.ps1` は**UTF-8 BOM付き**で保存する |
| k6 は閾値を設定したサブメトリクスしかサマリに出さない | タグで分けたのに数字が出てこない | 取り出したい分割ごとに `thresholds` を置く |
| シナリオがアプリの仕様に反した操作をする | 自分の投稿へのいいねは400、削除済み投稿へのいいねは404。**シナリオ側の不備をアプリのエラー率として数えてしまう** | `isMine` と `deleted` を除外する |
| 状態を戻さないシナリオ | 「いいね→取り消し」がシード済みのいいねを削り、長時間実行でデータが痩せる | 元々いいねされていない対象だけを選ぶ |
| ログインを毎イテレーション実行する | BCrypt(cost 10)が測定値を支配し、クエリ性能が数字に現れない | VUごとに1回だけ。ストレス・スパイクは事前認証を使う |
| `max_query_sec` にアイドル接続が混ざる | 「95秒かかるクエリがある」という誤った数字 | `FILTER (WHERE state = 'active')` を付ける |

## 行わないこと

- **アプリ本体のコード(`backend/src/`、`frontend/src/`)を変更しない。** このskillは計測とレポートまで。改善の実装は別作業として切り出す(計測と改善を同時にやると効果測定の土台が無くなる)。
- **既存の `docker-compose.yml` を変更しない。** 性能テストの都合で開発環境の起動手順を変えない。
- **開発用DB `sns_application` に書き込まない。** 読み取りの件数確認のみ。
- **`down -v` を開発用スタックに対して実行しない。** 必ず `-p snsapp-perf -f docker-compose.perf.yml` を付ける。
- **スモークを飛ばして本番計測に入らない。** データ量を上げてから失敗すると「スクリプトのバグか、アプリの限界か」が切り分けられなくなる。
- **絶対値を本番の性能保証として報告しない。** ローカル実施であることをレポートの冒頭と結論の両方に明記する。
